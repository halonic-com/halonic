# Plugins: one manifest, and an integration is a plugin with only a backend

- **Status:** Proposed
- **Date:** 2026-11-09
- **Deciders:** Liam (CTO); the board decided scope, UI model, sources and the name on HAL-1676
- **Source:** HAL-1669 (design document), HAL-1600 point 9 (Docker extensions)

## Context

People want to add things to Halonic that we don't ship: a service's tools, a
program on their own computer, a card or a form in Studio. We already have one
way to add the first of these, the integration ([integration interface](2026-11-08-integration-interface.md)),
and we must not build a second extension system next to it.

Docker's extensions show the shape that works (one `metadata.json`, optional
parts) and the parts that cost the most: container images as the delivery
format, programs copied onto the user's computer for every OS, and a web app
per extension loaded into the window.

The board decided on HAL-1676 (9 Nov 2026):

1. Plugins are part of **v0.1**.
2. Plugin UI is **declarative only**: Studio draws it from the manifest. No
   plugin code runs in the Studio window, and there is no web panel for now.
3. Plugins come from a **folder or a git repository only**. No npm, no list.
4. Users see the word **"plugin"**, and integrations are shown as one kind of
   plugin.

We looked at three options: declarative plugins (this record), declarative
plugins plus a sandboxed web panel, and plugins as in-process Studio features.
The second adds a versioned message API and a new attack surface; the third
gives no isolation at all.

## Decision

### 1. A plugin is a folder with one `plugin.yaml`

`plugin.yaml` is the whole contract between a plugin and Halonic. It declares
`id`, `version` (the plugin's own, `major.minor.patch`), `sdk`, `name`,
`description`, and at least one of three optional parts:

| Part         | What it is                                        | Where it runs                                       |
| ------------ | ------------------------------------------------- | --------------------------------------------------- |
| `backend`    | code that calls outside services and offers tools | the I5 isolated worker, through the integration kit |
| `localTools` | an MCP server over stdio on the user's computer   | a `Sandbox` session, after the trust gate           |
| `ui`         | settings, commands, cards and at most one panel   | nowhere: Studio draws it from the data              |

- `plugin.yaml` is a **file kind in `core/format`** (`kinds/plugin/`), built
  on `core/schema-kit`. Every object is strict, so an unknown field is an
  error. `halonic validate`, the JSON Schema and the golden tests cover it
  like every other kind.
- The `backend` block **is the integration sheet**, checked by the same
  `IntegrationSheet` schema, not a copy of it.
- Checks one schema can't make run in the loader and come back as
  `LoadProblem`s: the backend's code matches its sheet; every `ui` command and
  card names a tool that exists; a `secret` setting names a declared secret;
  no two parts offer a tool with the same name.

### 2. An integration is a plugin with only a backend

The loader reads an existing `integration.yaml` as a `plugin.yaml` that has
only the `backend` block. Nothing in `halonic-com/integrations` changes. The
integration guide's rules, the conformance suite, the AI integration builder
(I4 to I7) and the publishing plan apply to plugin backends unchanged. Model
providers and knowledge sources are plugins too, so one install, trust and
update path covers all of them.

### 3. The SDK is `IntegrationHost`, and no port is added

Plugin code gets `http`, `tokens`, `settings` and `wait`, exactly as an
integration does, and returns an `IntegrationConnection`. There is no file
system, no `Secrets`, no raw `fetch`, no timer and no access to Studio or the
workspace. A plugin that needs more is a local tool, fenced by the sandbox.

`sdk` equals the `Integration` port version (`integrationVersion`, now 1). The
port list's freeze rule therefore covers the plugin SDK: new optional fields
keep the number, a breaking change bumps it and comes with a record. The
manifest has no version field of its own; `sdk` tells the loader which schema
to read.

Layers:

| Package                    | What it gets                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| `core/format`              | the `plugin` file kind                                                                      |
| `core/ports`               | nothing: `Integration`, `Sandbox`, `TrustStore` and `ConnectorClient` cover it              |
| `core/app`                 | `PluginService`: find, validate, cross-check, trust, add tools, give `ui` to Studio as data |
| `adapters/integration-kit` | unchanged; it runs backends                                                                 |
| `adapters/sandbox-*`       | unchanged; they run local tools                                                             |
| `studio/features/plugins`  | turns `ui` data into shell contributions, drawn with `studio/kit`                           |
| `testing/integration`      | grows into the plugin conformance suite                                                     |

### 4. Local tools run only in a `Sandbox` session

This is the process launcher that the integration ADR left for later. A local
tool is an MCP server over stdio, started by a pinned package runner (`npx`,
`uvx`, the pin kept in the trust record) or by a script in the plugin folder.
It runs through `SandboxSession` with `stdin` and `stdout` as the transport,
never directly on the host.

Halonic builds the sandbox profile, never the plugin: a fresh working folder
per plugin, an empty environment, network limited to the bridge plus the
hosts in `localTools[].network`, and the time limit from `limits`. A blocked
access becomes a `sandbox.blocked` event. Where no `Sandbox` adapter works
(Android, the browser), the plugin still loads and its local tools show as
needing the desktop app.

### 5. UI is data, drawn by Studio

Each `ui` entry maps onto a shell point that exists today:

| `ui` entry          | Shell point      | Drawn as                                    |
| ------------------- | ---------------- | ------------------------------------------- |
| `settings`          | settings section | fields; a `secret` setting goes to Secrets  |
| `commands`          | command palette  | an optional form, then the result in a card |
| `cards`             | cards            | text, sanitised Markdown or a simple table  |
| `panel` (at most 1) | panel window     | a list of the plugin's cards and commands   |

Every value a plugin shows is untrusted text. It never becomes HTML or script,
and links go through `ExternalLink`. A broken plugin fails with a `ShellError`
that names it, and the rest of Studio keeps working. A sandboxed web panel, if
we ever add one, comes as a new optional field, so plugins written to this
record never change.

### 6. Installed from a folder or git, trusted like a workspace

- `halonic plugin add <folder | git URL>` copies the folder, or clones the
  repository at one commit through the hardened git adapter, into the
  profile's plugin folder, **never into a workspace**, and records the
  SHA-256 of every file. `halonic plugin list` and `halonic plugin remove`
  complete the set. Studio offers the same through `PluginService`.
- The trust fingerprint covers the normalised manifest plus every file hash.
  The prompt shows hosts, secrets and where they go, tools with their `risk`,
  and local programs with their pins and network. `TrustRecord.content` keeps
  what was shown.
- Any change to the manifest, a file or a pin changes the fingerprint, so the
  plugin is off until the person trusts it again, and the prompt shows what
  changed. `halonic trust --remove` revokes it.
- There are two fences and no third: the integration kit and the I5 worker
  for backend code, the sandbox for local programs. The UI carries no code.

**What moves.** Nothing in the order of other v0.1 work. Plugin tasks rank
below the critical path, so each owner finishes their current v0.1 work
first. That is where the delay comes from: P7 adds 5–7 days to Elena, who is
on the Studio critical path; P5 waits on `sandbox-srt`, which hasn't started
and carries the plan's biggest risk (Windows); P10 adds to Julian's review
queue before the release candidate.

**What goes to a later step, decided here.** A workspace naming the plugins
it uses (`plugins:` in `workspace.yaml`) waits until after v0.1, so v0.1 has
no workspace file format change. Plugins are still installed per profile.

**Rough added time to the v0.1 date:**

- with all three parts: **about 1.5 to 2 weeks later**;
- with local tools (P5 and their share of P10) moved to the first update
  after v0.1: **about 1 week later**, and plugins no longer depend on
  `sandbox-srt`'s Windows risk.

That is a noticeable slip, so the choice goes back to the board through
Chief (HAL-1731). Until the board answers, P5 waits, and everything else
starts.

## Consequences

- One extension system: integrations, model providers, knowledge sources and
  plugins share one manifest family, one trust path and one test suite.
- No new port and no new public API apart from `plugin.yaml` itself. The
  shell's points stay internal and can change with a pull request.
- Plugin authors write YAML and, if they need it, a small backend against
  `@halonicjs/integration-kit`. No bundler, framework or web app.
- Plugins can't draw arbitrary screens. That is on purpose; the web panel is
  the planned way out if a real plugin needs one.
- Checks that keep this true: the strict `plugin` schema and its golden
  tests; the plugin conformance suite, including attack tests (undeclared
  host, file read, key leak, a local tool reaching a host it didn't declare);
  a Studio test that plugin text never renders as HTML; a trust test that any
  changed file disables the plugin.

## Changed from an earlier decision

This extends the [integration interface](2026-11-08-integration-interface.md)
and changes none of its decisions:

- `integration.yaml` stays valid and is read as a backend-only plugin.
- Its deferred "process-launcher port for stdio MCP servers" arrives as
  plugin local tools, on the existing `Sandbox` port instead of a new one.
