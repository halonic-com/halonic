# Plugins: one manifest, and an integration is a plugin with only a backend

- **Status:** Accepted
- **Date:** 2026-11-09
- **Deciders:** Liam (CTO); the board decided scope, UI model, sources and the name on HAL-1676, and the v0.1 date on HAL-1731
- **Source:** HAL-1669 (design document), HAL-1600 point 9 (Docker extensions)

## Context

People want to add things to Halonic that we don't ship: a service's tools, a
program on their own computer, a card or a form in Studio. We already have one
way to add the first of these, the integration ([integration interface](2026-11-08-integration-interface.md)),
and we must not build a second extension system next to it.

Docker's extensions show the shape that works (one `metadata.json`, optional
parts) and the parts that cost the most: container images as the delivery
format, programs copied onto the user's computer for every OS, and a web app
per extension loaded into the window.

The board decided on HAL-1676 (9 Nov 2026):

1. Plugins are part of **v0.1**.
2. Plugin UI is **declarative only**: Studio draws it from the manifest. No
   plugin code runs in the Studio window, and there is no web panel for now.
3. Plugins come from a **folder or a git repository only**. No npm, no list.
4. Users see the word **"plugin"**, and integrations are shown as one kind of
   plugin.

On HAL-1731 (9 Nov 2026) the board chose **all three parts in v0.1**,
including local tools, and accepted that v0.1 moves about 1.5 to 2 weeks.

We looked at three options: declarative plugins (this record), declarative
plugins plus a sandboxed web panel, and plugins as in-process Studio features.
The second adds a versioned message API and a new attack surface; the third
gives no isolation at all.

## Decision

### 1. A plugin is a folder with one `plugin.yaml`

`plugin.yaml` is the whole contract between a plugin and Halonic. It is a
**file kind in `core/format`** (`kinds/plugin/`), built on `core/schema-kit`.
Every object is strict, so an unknown field is an error. `halonic validate`,
the JSON Schema and the golden tests cover it like every other kind.

```yaml
id: weather # lower-case words joined by "-", as an integration id
version: 1.2.0 # the plugin's own version, major.minor.patch
sdk: 1 # the Integration port version it was built for
name: Weather # shown to people
description: Forecasts for the places you name.
backend: { … } # optional, section 1.1
localTools: […] # optional, section 1.2
ui: { … } # optional, section 1.3
```

At least one of `backend` and `localTools` is required: a plugin with only
`ui` has nothing for its forms and cards to call.

#### 1.1 `backend`

`backend` is the integration sheet without `id`, `version` and `kit`. The
loader fills those three from the plugin's `id`, `version` and `sdk`, so each
number is written once. It adds one field the sheet doesn't have:

- `entry`: the built JavaScript module in the plugin folder that exports the
  `Integration`, default `backend/index.js`.

`provides` defaults to `[connector]`. The `plugin` kind's schema is built from
`IntegrationSheet` (omit three fields, add `entry`, default `provides`), not
copied, so a change to the sheet reaches plugins by itself. The existing
`integration` kind and its golden tests don't change.

A plugin's `backend` **refuses `needs: process`**. Starting a program is what
`localTools` is for, and only there does it run in the sandbox.

#### 1.2 `localTools`

Each entry is one MCP server over stdio:

```yaml
localTools:
  - id: files # unique in the plugin
    start: # exactly one of package or script
      package:
        runner: npx # npx or uvx
        name: "@acme/files-mcp"
        version: 3.1.4 # exact; no range, no tag
        registry: https://registry.npmjs.org/ # optional; the runner's public registry by default
      # script: { program: node, path: tools/server.js }   # a file in the plugin folder
    args: ["--read-only"]
    env: # variable → a setting or a declared secret, never a literal value
      ACME_ROOT: { setting: root }
      ACME_KEY: { secret: acme-key }
    secrets: # same shape as the sheet's secrets, without `as`
      acme-key: { purpose: Reads your Acme account, hosts: [api.acme.com] }
    network: [api.acme.com] # hosts it may reach, besides the bridge
    callTimeoutMs: 60000 # one tool call; default 60 s, at most 1 h
    tools: # every tool it offers, with the sheet's Tool shape
      - name: list-files
        description: Lists the files in a folder.
        risk: read
        untrusted: true
```

- **Tools are declared in the manifest.** The trust prompt and the
  cross-checks need the names, `risk` and `untrusted` before anything runs. At
  run time Halonic offers only declared tools, with the manifest's
  description; a tool the server lists but the manifest doesn't is refused and
  logged.
- **Pins.** A `package` start is a pin. The pin goes into the trust record and
  is turned into `ConnectorTransport.stdio.pin`, so every pin rule of the
  connector port applies unchanged: exact version, its own registry, an empty
  folder, the workspace's package-manager settings ignored, and the
  environment deny list. A `script` start runs a file whose hash is part of
  the fingerprint.
- **Time.** The sheet's `limits` are HTTP limits and don't apply here.
  `callTimeoutMs` bounds one call. The session's `timeLimitMs` is set by
  Halonic, not by the plugin; when it runs out, the server starts again on the
  next call.

#### 1.3 `ui`

```yaml
ui:
  settings: # name → field; the values go to the backend as host.settings
    units: { label: Units, type: choice, choices: [metric, imperial], default: metric }
    root: { label: Folder, type: text, required: true }
    acme-key: { label: Acme key, type: secret, secret: acme-key }
  commands:
    - id: forecast
      title: Show the forecast
      tool: forecast # a declared tool
      form: # optional; field name = tool argument
        place: { label: Place, type: text, required: true }
      show: table # text, markdown or table; how the result is drawn
  cards:
    - id: today
      title: Today
      tool: today # must be a `read` tool
      args: { place: home } # fixed values only
      show: markdown
  panel: { title: Weather } # optional, at most one
```

- **Field types:** `text`, `url`, `number`, `boolean`, `choice` (with
  `choices`) and `secret` (with `secret`, the name of a secret declared in
  `backend.secrets` or a `localTools[].secrets`). Each field may have `help`,
  `required` (default `false`) and `default`; a `secret` field has no default.
  A command form takes every type except `secret`.
- **Commands** go into the command palette. A command opens its form if it
  has one, calls its tool, and draws the result as a card in the plugin's
  panel, or in a dialog when the plugin has no panel.
- **Cards** show only in the plugin's own panel in v0.1. They call a `read`
  tool with fixed arguments when the panel opens. The shell's selection cards
  (`CardContribution.for`) are not offered: a card for a selected agent or run
  would hand that item to plugin code, which is workspace access the SDK
  doesn't give.
- **The panel** lists the plugin's cards, then its commands, in manifest
  order. Without `panel`, cards are an error and commands still work.

#### 1.4 Checks in the kind and checks in the loader

Checks inside one `plugin.yaml` run in the kind's `check` and come back as
`KindCheckProblem`s, like every other kind: every command and card names a
declared tool; a card's tool is `read`; a `secret` field and an `env` secret
name a declared secret; an `env` setting names a declared setting; tool names
and local tool ids are unique across all parts; `panel` is present when
`cards` is.

Checks that need the backend's code stay where they are today, in the
integration kit's loader, and come back as `LoadProblem`s: the code's tools
match `tools`, and its declarations match the sheet.

#### 1.5 An `integration.yaml` read as a plugin

The loader reads an existing `integration.yaml` as a plugin with only a
`backend`. Its `name` is its `id` and its `description` is empty; `kit`
becomes `sdk`, and `entry` keeps the integration's current place. An
integration that wants a proper name switches to `plugin.yaml`. A folder with
both files is a load error.

### 2. An integration is a plugin with only a backend

Nothing in `halonic-com/integrations` changes. The integration guide's rules,
the conformance suite, the AI integration builder (I4 to I7) and the
publishing plan apply to plugin backends unchanged. Model providers and
knowledge sources are plugins too, so one install, trust and update path
covers all of them.

### 3. The SDK is `IntegrationHost`, and no port is added

Plugin code gets `http`, `settings` and `wait`, exactly as a local
integration does in the I5 worker, and returns an `IntegrationConnection`.
There is no file system, no `Secrets`, no raw `fetch`, no timer and no access
to Studio or the workspace. A plugin that needs more is a local tool, fenced
by the sandbox.

**No tokens in v0.1.** A plugin backend from a folder or git always runs in
the I5 worker, and no token value enters the worker (I5 design, section 3.5).
So the loader refuses a plugin whose `backend` declares `tokens`, with the
same message as for a local integration: "An integration you build or change
can't hold sign-in secrets yet." The fix names the place to change: "Remove
tokens from its backend and use an API key, or ask for sign-in support."
Secrets still work: Halonic places them in requests, and the plugin never sees
the value. Tokens as handles, with sign-in run by Halonic, is the follow-up
HAL-984; a plugin backend gets them when local integrations do. Only built-in
backends, reviewed code that ships with Halonic and runs in-process, keep
`tokens`, as built-in integrations do.

`sdk` equals the `Integration` port version (`integrationVersion`, now 1). The
port list's freeze rule therefore covers the plugin SDK: new optional fields
keep the number, a breaking change bumps it and comes with a record. The
manifest has no version field of its own; `sdk` tells the loader which schema
to read.

**Where plugin data is kept.** Plugins, their setting values and their trust
records live in the person's profile, never in a workspace. Setting values
are stored by `PluginService` in a `RecordStore` keyed by plugin id; secret
values go to `Secrets` under the plugin's own name, `plugin__<id>__<secret>`,
which `PluginService.secretNames` gives (HAL-4540). So a plugin reads only the
secrets stored for it, never one a person stored for something else, and
Remove knows what to delete: the host deletes those names with its own secret
writer, since `Secrets` stays read-only in core. The doubled `_` is needed
because `Secrets` takes `-` and `_` as the same, and kebab names never hold
two `-` in a row. To fit the 128-character name rule, a plugin's id is at
most 48 characters and a secret it declares is named in at most 64.
`TrustRecord` works for a plugin folder
unchanged: `location` is the folder's real path, `fingerprint` is the plugin
fingerprint (section 6), and `content` is what the prompt showed.

**One optional field, no new port.** Nothing on `main` connects an MCP client
to a `SandboxSession` yet, because `ConnectorFactoryContext` has no sandbox.
P5 adds:

- an optional `sandbox?: SandboxSession` on `ConnectorFactoryContext`. When it
  is set, a `stdio` connector starts its program in that session and nowhere
  else. An optional field keeps `connectorClientVersion` under the freeze
  rule;
- a new adapter, `adapters/connector-stdio-sandbox`, the `stdio`
  `ConnectorFactory` that starts the program through the session, with the
  pin rules of `ConnectorTransport.stdio.pin` unchanged. It refuses to start
  a plugin's local tool without a session.

Layers:

| Package | What it gets |
| --- | --- |
| `core/format` | the `plugin` file kind |
| `core/ports` | one optional field, `ConnectorFactoryContext.sandbox`; no new port |
| `core/app` | `PluginService`: find, validate, cross-check, trust, add tools, give `ui` to Studio as data |
| `adapters/integration-kit` | unchanged; it runs backends |
| `adapters/connector-stdio-sandbox` | new; it runs local tools in a `SandboxSession` |
| `adapters/sandbox-*` | unchanged; they fence local tools |
| `studio/features/plugins` | turns `ui` data into shell contributions, drawn with `studio/kit` |
| `testing/integration` | grows into the plugin conformance suite |

### 4. Local tools run only in a `Sandbox` session

This is the process launcher that the integration ADR left for later. A local
tool runs through `SandboxSession` with `stdin` and `stdout` as the transport,
never directly on the host.

Halonic builds the sandbox profile, never the plugin: a fresh working folder
per local tool, an environment with only the `env` entries, network limited to
the bridge plus `network`, and the session time limit. The session proves its
fence before it opens ([sandbox fence proof](2026-11-09-sandbox-fence-proof.md)).
A blocked access becomes a `sandbox.blocked` event. Where no `Sandbox` adapter
works (Android, the browser), the plugin still loads and its local tools show
as needing the desktop app.

### 5. UI is data, drawn by Studio

Each `ui` entry maps onto a shell point that exists today:

| `ui` entry | Shell point | Drawn as |
| --- | --- | --- |
| `settings` | settings section | fields; a `secret` field goes to Secrets |
| `commands` | command palette | an optional form, then the result in a card |
| `cards` | the plugin panel | text, sanitised Markdown or a simple table |
| `panel` (at most 1) | panel window | the plugin's cards, then its commands |

Every value a plugin shows is untrusted text. It never becomes HTML or script,
and links go through `ExternalLink`. A broken plugin fails with a `ShellError`
that names it, and the rest of Studio keeps working. A sandboxed web panel, if
we ever add one, comes as a new optional field, so plugins written to this
record never change.

### 6. Installed from a folder or git, trusted like a workspace

- `halonic plugin add <folder | git URL>` copies the folder, or clones the
  repository at one commit through the hardened git adapter, into the
  profile's plugin folder, **never into a workspace**, and records the
  SHA-256 of every file. `halonic plugin list` and `halonic plugin remove`
  complete the set. Studio offers the same through `PluginService`.
- The trust fingerprint covers the normalised manifest plus every file hash.
  The prompt shows hosts, secrets and where they go, tools with their `risk`,
  and local programs with their pins and network.
- Any change to the manifest, a file or a pin changes the fingerprint, so the
  plugin is off until the person trusts it again, and the prompt shows what
  changed. `halonic trust --remove` revokes it.
- There are two fences and no third: the integration kit and the I5 worker
  for backend code, the sandbox for local programs. The UI carries no code.

## What this does to v0.1

Plugins in v0.1 are about **36 agent-days (31 to 42)**, split over ten tasks
and six people. Priya's review moved P2 to 5–6 days, which stays inside the
range:

| Step | Owner | Agent-days | Waits for |
| --- | --- | --- | --- |
| P1 `plugin` kind and its checks | Priya | 2–3 | this record |
| P2 `PluginService` in `core/app` | Priya | 5–6 | P1, the trust gate (HAL-188) |
| P3 install from folder or git, `halonic plugin` | Tomas | 3–4 | P2 |
| P4 backends in the I5 worker | Ravi | 2–3 | P2, the I5 runner (HAL-983) |
| P5 local tools on `Sandbox`, the sandboxed stdio adapter | Owen | 5–7 | P2, `sandbox-srt` (HAL-193) |
| P6 plugin screens designed and approved | Sofia | 2–3 | the board's approval of the screens |
| P7 `studio/features/plugins`; integrations shown as plugins | Elena | 5–7 | P2, P6, the kit (HAL-1289) |
| P8 plugin conformance suite and a sample plugin | Tomas | 3–4 | P1 |
| P9 author guide, glossary entry, security page | Maya | 2 | P8 |
| P10 security review and attack tests | Julian | 3–4 | P4, P5, P7 |

**What moves.** Nothing in the order of other v0.1 work. Plugin tasks rank
below the critical path, so each owner finishes their current v0.1 work
first. That is where the delay comes from: P7 adds 5–7 days to Elena, who is
on the Studio critical path; P5 waits on `sandbox-srt`; P10 adds to Julian's
review queue before the release candidate.

**What goes to a later step, decided here.** A workspace naming the plugins
it uses (`plugins:` in `workspace.yaml`) waits until after v0.1, so v0.1 has
no workspace file format change. Plugins are still installed per profile.

**The v0.1 date.** The plan has no calendar date for v0.1; the release
candidate follows the critical path. With all three parts, the board's
choice, it comes **about 1.5 to 2 weeks later** than it would have without
plugins.

**The Windows sandbox risk.** With local tools in v0.1, the date now also
depends on `sandbox-srt` working on Windows, the plan's biggest risk. We keep
it small this way:

1. `sandbox-srt` (HAL-193) does Windows first: the fence proof passes in CI
   on a Windows runner before the macOS and Linux polish.
2. P5 doesn't wait for it. Owen builds and tests against the in-memory
   `Sandbox` and the Linux adapter; only the Windows run of the conformance
   suite waits.
3. A checkpoint: if the Windows fence proof isn't passing in CI by the time
   P2 merges, Liam takes it to the board through Chief before the slip grows
   past 2 weeks. The fallback that keeps the date is local tools showing as
   "not available on Windows yet", as they do on Android; that is a scope
   change, so it is the board's choice, not ours.

## Consequences

- One extension system: integrations, model providers, knowledge sources and
  plugins share one manifest family, one trust path and one test suite.
- No new port. One optional field on `ConnectorFactoryContext`, one new
  adapter, and `plugin.yaml` itself as the only new public contract. The
  shell's points stay internal and can change with a pull request.
- Plugin authors write YAML and, if they need it, a small backend against
  `@halonicjs/integration-kit`. No bundler, framework or web app.
- Plugins can't draw arbitrary screens or show cards next to a selection.
  That is on purpose; the web panel and selection cards are later, each with
  its own record.
- Checks that keep this true: the strict `plugin` schema and its golden
  tests; the plugin conformance suite, including attack tests (undeclared
  host, file read, key leak, a local tool reaching a host it didn't declare,
  a local tool offering a tool it didn't declare); a Studio test that plugin
  text never renders as HTML; a trust test that any changed file disables the
  plugin.

## Changed from an earlier decision

This extends the [integration interface](2026-11-08-integration-interface.md)
and changes none of its decisions:

- `integration.yaml` stays valid and is read as a backend-only plugin.
- Its deferred "process-launcher port for stdio MCP servers" arrives as
  plugin local tools, on the existing `Sandbox` port instead of a new one.
