# @halonicjs/app-agent-host

Halonic's agent host as one Node program. It unpacks its files and serves on loopback, with a token made for each launch. It serves `GET /v1/health`, the `Sandbox` port, the Halonic bridge and the harnesses (Claude Code and Codex).

- **Layer:** apps
- **Owner:** owen
- **Public API:** `@halonicjs/app-agent-host`

## Build one executable

```
pnpm --filter @halonicjs/app-agent-host build:sea
pnpm --filter @halonicjs/app-agent-host smoke:sea
```

`build:sea` turns `src/main.ts` into plain JavaScript and makes `dist/halonic-agent-host` (`.exe` on Windows) with Node's own single-executable support (`node --build-sea`), so no extra library is needed. It first builds the integration runner (`dist/runner.mjs`, one file no import reaches) and embeds it as a second payload program, so the host can start a plugin's backend with the executable standing in for Node. The Node that runs the build is the base of the executable, so build with the Node the repo pins. `smoke:sea` runs the executable in each of its uses below with a fresh profile folder, checks what it prints and reports its size. CI does both on Linux, macOS and Windows.

## The payload

The host can't be one bundled file: sandbox-runtime finds its own programs (`apply-seccomp`, `srt-win.exe`) next to its code and runs as a separate Node program, so it needs real files on disk. So the entry point imports nothing, and the build embeds the files the host runs from as the executable's assets, one asset per file, keyed by its path in the payload:

- the host's own `src`, without tests and without `src/build`. A test is a `.test` or `.spec` file, a test helper, a top-level `test/` folder, or anything under a `fixtures/`, `golden/` or `__snapshots__/` folder (`commands/test/` isn't one: it holds a command the host runs);
- every workspace package it depends on, at the same place as in the repo (`packages/core/ports/...`), with its `package.json` and its `src` without tests, by the same rule;
- every outside package those depend on, under `node_modules/`, without source maps and type declarations. Only `dependencies` and `optionalDependencies` count. Two copies of one outside package stop the build.

The build puts the payload's manifest (each file's SHA-256, size and executable mark, one digest of them all, the host's entry and the programs) in front of the entry point, as it does the version.

## Running it

```
halonic-agent-host --profile-folder <folder> [--version | --sandbox-check | --sandbox-setup | --sandbox-remove | --sandbox-take-back]
halonic-agent-host --profile-folder <folder> [--keychain-relay] [--sweep-root <folder> …]
halonic-agent-host --profile-folder <folder> --stdio --relay-host 127.0.0.1:<port> [--keychain-relay] [--sweep-root <folder> …]
halonic-agent-host --profile-folder <folder> --messaging-only [--keychain-relay] [--sweep-root <folder> …]
halonic-agent-host <unpacked program> [arguments]
```

With `--version` the host prints its version. Without any of these, it serves on loopback (below); with `--stdio`, over its standard input and output. The sandbox commands print one JSON line, and exit with 0 when it says `ok` and 1 when it doesn't, so an installer can go by the exit code alone:

| Command | Prints |
| --- | --- |
| `--sandbox-check` | whether the sandbox works on this machine: `{"ok":true,"reason":null,"missing":[]}`, or `ok` false with the reason and what is missing |
| `--sandbox-setup` | `{"ok":true}` once the one-time setup worked and the sandbox check passes, or `{"ok":false,"reason":"<one line>"}` |
| `--sandbox-remove` | `{"ok":true}` once what the setup left is removed (or nothing was set up), or `{"ok":false,"reason":"<one line>"}` |
| `--sandbox-take-back` | what it did with the access a removal with administrator rights kept: `{"ok":true,"outcome":"taken_back"}` or `"none"`, or `ok` false with `"elevated"` or `"failed"` |

`--sandbox-setup` is for the Windows installer, which runs it as an administrator: it runs srt's Windows install without srt's profile read grant, then the check (see sandbox-srt's README). The install is for the whole machine, so a check as the person's own account passes after an administrator answered the prompt. Running it again repairs the install or changes nothing. On other systems there is nothing to set up, and it exits with 1.

`--sandbox-remove` is for the Windows uninstaller, which runs it as an administrator, once (and for Settings › Remove the sandbox). It runs srt's Windows uninstall: the sandbox account and its profile, the `sandbox-runtime-users` group, the network filters, the `HKLM\SOFTWARE\sandbox-runtime` key, and the write grants kept on project folders by sessions of the user it runs as. It is `ok` when nothing was set up, and when run again. While a sandboxed program runs, srt removes nothing and says so. srt leaves `%ProgramData%\sandbox-runtime` (its CA key folder) in place. On other systems there is nothing to remove, and it exits with 0.

`--sandbox-take-back` is for the Windows installer, which runs it as the person installing, before its sandbox step and whether or not that step is ticked (HAL-16084). When a removal with administrator rights kept srt's grants for this user and srt's sandbox account is gone, it takes them back (`profile forget`, `acl forget --all`), as the host does at its start. It must come before the sandbox step: once that step recreates srt's account, srt no longer reports the grants as left behind, and nothing takes them back. With administrator rights it takes nothing back and says `elevated`. On other systems it says `none`.

**The remote gateway (HAL-10827).** Off in every launch the executable makes: no argument, environment variable or setting turns it on, because it has no pairing yet and anything on this computer could otherwise list sessions, send prompts and answer approvals. Only code that calls `run` with a gateway setting starts it, which tests do; it is for phase B to give the person a switch, once pairing is there. Every connection runs inside the end-to-end session (`SecureSession`, HAL-12238), so nothing is read or answered in the clear; until the pairing service and the phone store exist (HAL-12237), the host opens no pairing and knows no phone, so every phone is refused, and its key is made fresh for each launch and kept in memory. When on, the listener (`adapters/remote-gateway`) takes a free loopback port or the one the setting names, and a listener that can't start is reported on standard error while the host serves without it. Over `--stdio` it stays off, because that mode listens on no port (HAL-5396). The gateway sees each run the host has going as a session (the run ledger): its prompt, answers, approvals and result as events numbered from 1, at most 500 per session, and the 20 latest finished sessions. Titles are cut to 80 characters and approval summaries to 300, and the session list holds only the newest sessions that fit in one reply of 65,519 bytes. The host judges each approval itself, and fails closed: every tool is `risky`, a read too, because a read can leave the working folder. A phone's prompt reaches the run through the same call Studio's answers use, but a phone's answer to an approval is refused for now: that call would skip the engine's own decision, so approvals reach the engine in a follow-up. On stop, the listener closes before the runs are cancelled. The gateway's port counts among the host's own, so no model provider's address may be that port.

**The host lock and the sweep (HAL-6256).** When it serves, the host takes the lock `<profile folder>/agent-host/host.lock` and holds it until it stops (the same lock rules as the engine's, so the lock of a host that crashed is taken over). Only the holder sweeps: right after it takes the lock, it forgets the kept Windows grants inside each `--sweep-root` that no live session of its own uses, those of sessions that crashed before they closed (see sandbox-srt's README). The launcher names the roots (Studio gives the profile folder and each folder the person has open); each must be absolute, or the host exits with 2. While another live host holds the lock (Studio launched twice, say), or the lock can't be taken, the host serves without a sweep and, when it was given a sweep root, says so on standard error. A sweep on Linux or macOS forgets no grants. On those, before it serves, the holder also removes the bridges' run folders under `<profile folder>/bridges` that a crashed host left behind (HAL-7302): only a private folder whose `bridge.sock` refuses a connection, or that has been empty for a minute, so another host's live bridges keep theirs. When that fails, it says why on standard error and serves all the same. The CLI takes the same lock, through the same `takeHostLock` of sandbox-srt, while its harness runs have sandbox sessions on Windows, and sweeps only while it holds it (HAL-6780, `cli.sandbox-kept-grants`); every session either one opens is in its process's kept-grant record first, so neither's sweep takes a live session's grant.

- **The host.** On launch the executable unpacks the payload into `<profile folder>/agent-host/<version>-<digest>` and checks every file against its SHA-256. A folder an earlier launch left is reused when every file still matches and it holds no file or folder the manifest doesn't name, and unpacked again otherwise. It unpacks into a temporary folder first and renames it, so a launch that stops halfway leaves nothing half-written. It then maps `@halonicjs/*` to the unpacked packages with a resolve hook and loads `src/host.ts`. The folder is inside Halonic's own data, so the profiles Studio builds must deny it to sandboxed programs, with the rest of that data (the `halonic-data` group). Studio's side isn't built yet; nothing on `main` builds that group so far.
- **Old folders.** More than one host can run on a profile folder (Studio launched twice, or the CLI next to it), so each host first claims its folder in `agent-host/running/<process id>` (written under a temporary `.writing` name and renamed, so a clean-up never reads a claim empty) and gives the claim up when it exits. Once its own folder is ready, the host removes the payload folders other versions and halfway launches left under `agent-host`, but never one a running host has claimed, nor that host's temporary folders. A claim whose host no longer runs is dropped, and anything that isn't a payload folder is left alone. This is best effort: a folder still in use (on Windows) stays until a later launch.
- **A payload program.** sandbox-srt starts srt's command line as `process.execPath <srt dist/cli.js>`, and here `process.execPath` is this executable. When the first argument is one of the manifest's programs inside a folder this version unpacked, and every file of the payload in that folder still has its digest and the folder holds nothing else (not only the program, which loads the files next to it), the executable runs it as Node would. The folder must also sit directly in an `agent-host` folder, so a folder that only has the right name isn't run. Any other argument isn't run.
  The whole payload is checked before the program runs, because it loads the rest of srt from the folder. That is as far as the check goes: the folder is in Halonic's own data, writable by your account, and a program that can write there can change the host's own files too, which no check here would stop. Keeping sandboxed agents out of it is the profile's job (above).
- **Workspace packages' `exports`.** The resolve hook reads a path, or conditions `node`, `import` or `default` that each name a path. Any other form (a list, `null`, nested conditions) stops the host with an error that names the package and the subpath.

## Serving on loopback

The program that starts the host (Studio) reads one line from its standard output:

```
{"url":"http://127.0.0.1:49152","token":"<43 characters>"}
```

The host listens on a free port of `127.0.0.1` only. The token is 32 random bytes in base64url, new at each launch, and goes only to that program on standard output: never in arguments, the environment or a file, where other programs could read it. A request gets in only when:

1. its `Host` header is `127.0.0.1:<port>` or `localhost:<port>`, so a web page that points its own domain at 127.0.0.1 (DNS rebinding) gets `421`;
2. it has no `Origin` header, so a request from a web page gets `403`; there is no CORS, because Studio's Rust side makes the requests;
3. its `Authorization` header is `Bearer <token>`, compared in constant time; otherwise `401`.

Every refusal comes before the path is looked at, so a caller without the token can't learn which paths exist. Answers are JSON; an error is `{"error":{"kind","message"}}`. The host stops when its standard input closes, so it never outlives the program that started it.

A request body is JSON of at most 1 MiB. A `Content-Length` over that gets `413` before any of the body is read, so a caller can't hold a request open by promising a body it never sends; a body without a length is counted as it arrives. A stream (the blocked accesses, the bridge's calls) never fills the host's memory either: when a caller keeps it open but stops reading, and more than 4 MiB wait to be sent, the host drops the connection and the route cleans up as if the caller had gone.

## The engine role's listener

The engine role (`halonic-agent-host --engine`, B1) serves the engine server of `host/server` (`createEngineServer`) through its own listener, `src/engine/engine-listener.ts`. The engine server makes the same three checks as above, in the same order, before it looks at the path, and answers errors as `{"code","message"}`. The listener adds what a socket needs:

| Rule | What it does |
| --- | --- |
| Loopback only | listens on a free port of `127.0.0.1`, as the host's server does |
| The host's limits | the same request times, connection cap (`defaultHostServerLimits`) and 1 MiB body size (`maxBodyBytes`) as the host's server |
| At most 8 open `GET /api/run-updates` streams | a new stream past them gets `503 too_many_streams`, after the token checks, so a caller without the token still gets `401`; an open stream is never dropped to make room, and a stream that closes frees its place |

The run-update streams follow a feed that reads the engine's runs once a second while any stream is open, and sends one `{ runId, status, seq }` frame per run whose status changed (`src/engine/run-updates-feed.ts`).

`halonic-agent-host --engine --profile-folder <folder> --workspace <folder>` starts the role (`src/engine/engine-command.ts`); any other argument exits with code 2. It opens the workspace's engine as `halonic routines watch` does, on the versions it watches, with the routine scheduler and the harness host, and takes `engine.lock`. What differs from the CLI:

- secrets and key origins come only from Studio's shell, over the control pipe, one read at a time; the engine keeps no value;
- trust is only read, never granted, through the read-only trust gate, for every start and every new version;
- whether a stored provider key may go to an address other than its default is read once, when the engine opens; after a trust change the shell restarts the engine;
- the profile folder is the one `--profile-folder` names, never `HALONIC_HOME`;
- a run calls no connector and no listed tool yet: those wait for the shell's approvals.

On `stop` it stops the scheduler and gives the steps 10 seconds. If they take longer, it gives `engine.lock` up, ends the runs left going as interrupted, writes `stopped`, and ends the process at once, so the step still going can't write after another engine took the lock.

## Serving over standard input and output

In Halonic's WSL distro the host must not listen on a port: every WSL 2 distro of a person shares one network, so a port in ours would be open to their own Ubuntu too (HAL-5396, condition W9 of HAL-5407). There Studio starts the host with `--stdio --relay-host 127.0.0.1:<port>`. Studio's relay listens on Windows' own loopback, as the host does elsewhere, and passes each connection it accepts to the host as frames over `wsl.exe`'s standard input and output. The host serves the same routes with the same checks and limits; it never calls `listen()`.

The host first prints one line, `{"token":"<43 characters>"}` (no `url`: the relay has the address). After it, standard output carries frames only, in both directions:

```
[connection id: u32 big-endian][kind: u8][length: u32 big-endian][bytes]
```

| Kind | Value | Bytes | Means |
| --- | --- | --- | --- |
| `open` | 1 | none | the relay accepted a connection; only the relay opens them |
| `data` | 2 | at most 64 KiB | the connection's bytes, in order |
| `end` | 3 | none | the sender sends no more on this connection (half-close) |
| `reset` | 4 | none | the sender dropped the connection; nothing more goes either way |

- **Ids.** Id 0 is the host's own, never a client's (see "The host's own secrets in the keychain" below); without `--keychain-relay`, any frame on it breaks the stream. The relay numbers its connections 1, 2, 3, …, and never reuses an id. A frame for an id that has closed (sent before the relay saw the host's `reset`) is dropped. An `open` for an id that isn't new, any other frame for an id never opened, an unknown kind or a length over 64 KiB breaks the stream.
- **`Host`.** A request must name the relay, `127.0.0.1:<port>` or `localhost:<port>` with the port of `--relay-host`, so DNS rebinding against the relay's port gets `421`. Without a `--relay-host` on `127.0.0.1` the host exits with 2.
- **Sign-in callbacks.** The only routes served without the token, and the only two shapes of request Studio's relay passes on without it. An integration's sign-in comes back to `GET /sign-in/<random>` (43 base64url characters) on the relay's port, with the same checks and page headers as Google's. Google's: over frames it is `GET /v1/google/callback` (on the host's own port, `/api/google/callback`), and the sign-in's redirect names the relay's port and that path. It has the same `Host`, `Origin` and `state` checks, and its page is sent with `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `Connection: close`, so the connection ends with the answer.
- **Limits.** The time limits apply as on loopback. The host keeps at most 256 connections open and answers an `open` past that with `reset`. All connections share one input, so the host can't make the relay wait on one: a connection with more than 4 MiB the host hasn't read yet is reset. The relay must read the host's output all the time, and keep a slow reader's backlog per connection.
- **Standard output is frames only.** Once the host serves, anything else that would print there goes to standard error.
- **Stop.** The host stops when its standard input ends, as on loopback, with exit code 0. When the stream breaks, it says why on standard error and exits with 1.

## The host's own secrets in the keychain

The host keeps secrets of its own: today `remote-host-key`, the static key paired phones pin. Started by the CLI, it keeps them in the profile's secrets file. Started by Studio with `--keychain-relay`, it keeps them in the OS keychain through Studio's shell, because the host can't reach the keychain itself (on Windows it runs inside Halonic's WSL distro). Requirement `agent-host.keychain-secrets`.

- **The channel.** After the handshake the host sends its requests on connection id 0: over the relay's frame stream with `--stdio`, and otherwise as the same frames on standard input and output, which then carry nothing else (anything else that prints goes to standard error). A request is one `data` frame holding `{"op":"get"|"set"|"delete","name":"remote_host_key"}` (with `"value"` for `set`); the shell answers on id 0 with `{"ok":true,"value":…}` or `{"ok":false,"kind":…,"message":…}`. The host sends one request at a time, never names anything but its own secrets, and stops when the shell sends anything but the answer it waits for. The shell's side is `studio.src-tauri.crates.agent-host.host-secrets-channel`.
- **Folders opened later.** The shell also sends, unasked, `{"op":"open_workspace","folder":…}` on id 0 when the person opens a folder after the host started. The host adds the folder's real path to its workspaces (as a `--sweep-root` would have, without a sweep) until it stops; a folder that doesn't exist, isn't a folder or is the profile folder is refused, and standard error says why, without the path. Either way the host then answers `{"op":"noticed","folder":…}` on id 0, and the shell waits for that answer before its next request, so the request finds the folder. A notice has exactly those two fields and an answer to a secret request never has `op`, so neither is taken for the other; the shell never takes `noticed` for a secret request. No route adds a workspace. Requirement `agent-host.opened-workspaces`.

## Messaging only

With `--messaging-only` the host serves `GET /v1/health` and the routes under `/v1/messaging/` and `/v1/paperclip/`, and answers `404 not_found` for every other path: no run, harness, sandbox, bridge, connector, model, plugin, file, Google or remote route. It takes no lock, sweeps nothing and makes no sandbox. Studio's shell runs it beside itself on Windows while the harnesses run in Halonic's WSL distro, so agent messaging keeps Windows paths and the Windows keychain. Requirement `agent-host.messaging-only`.
- **No fallback.** When the keychain can't be used, the host fails with the shell's reason; it never writes the secrets file instead.
- **The move out of the file.** When it starts serving, and before the first use, the host moves each of its secrets out of the secrets file: written to the keychain, read back and compared, and only then removed from the file. When both hold the same value, the file's copy goes. When they differ, neither changes, the host says that the keychain's value wins, and it refuses to use the secret until only one is left. What it says never holds a value or a hash of one.

## The sandbox over loopback

Studio gives the engine a stand-in `Sandbox` that calls these routes, and the host runs the real one (`SrtSandbox`). The profile arrives as data, so the host checks it before the sandbox sees it: every field present, nothing extra, every path absolute (`400 body_invalid` names each problem with its path). A session that can't open gets `422 sandbox_open_failed` with the sandbox's reason.

A session is named by an id the host makes; any other id gets `404 unknown_session`. When a session's time limit runs out, the host closes it: its id is forgotten and its blocked stream ends. The host keeps at most 64 sessions open, counting those still opening; past that, opening one answers `429 too_many_sessions`. A `timeLimitMs` above 2,147,483,647 (about 24.8 days, the longest a timer can hold) is refused. When the host stops, it closes every open session before it stops serving, so no sandboxed program outlives it.

## Sessions on this computer

An agent a person set to "On this computer" runs without the sandbox, with all the person's rights, so `POST /v1/sandbox/this-computer/open` opens its session only once the host's gate passes (`agent-host.unfenced-gate`). Everything in the request is a claim: the host reads the agent's file, the person's trust record, their "On this computer" choice and their instruction trust from disk itself, and the profile must be one the host built for that agent, with its own instructions and proposal folders. The open then takes the profile, so it opens one session, with the launcher the CLI uses (`createHostSandbox()`). A run in the session starts only for that agent and with the host's own environment (`agent-host.unfenced-start`).

## The bridge over loopback

`harness-bridge` runs here, next to the sandbox whose program calls it, but the engine's recorder, tools, approvals and provider keys stay in Studio. Studio opens a bridge for one run with `{ runId, agentId, providers, prices, runsOn }`; `runsOn` is where the run's program runs (`sandbox` when left out), and `prices` is each provider's models with a price, because the bridge asks for a price without waiting. The answer stays open as a stream:

```
{"type":"opened","bridge":"<id>","url":"http://bridge.halonic.invalid","token":"<run token>","socketPath":"<profile>/bridges/<run>/bridge.sock"}
{"type":"call","call":"1","method":"secrets.get","params":{"name":"anthropic-key"}}
{"type":"call","call":"2","method":"recorder.record","params":{"type":"llm.request",...}}
{"type":"cancel","call":"3"}
```

The first line is `opened`, or `{"type":"failed","message"}` when the bridge couldn't listen. When the error has a kind or a typed cause, `failed` carries them too, as `kind` and `failureCause` (`{ code, detail }`, such as `harness-bridge.socket-path-too-long` with the path's length and the system's limit), so the run records why it failed as it would with the bridge in Studio's own process. On Linux (WSL's distro included) and macOS each bridge serves a Unix socket in a new private folder under `bridges` in the profile folder (`--profile-folder`), and `opened` gives its `socketPath`: the sandbox keeps the program off the host's loopback ports there, and srt's proxy sends the bridge's name, `bridge.halonic.invalid`, to the socket. A bridge opened with `"runsOn":"this-computer"`, for an agent a person set to run on this computer, has no sandbox or proxy in front of it and always listens on a loopback port, which the launcher accepts; its token still guards it (`agent-host.bridge-place`). On Windows, or without a profile folder, every bridge listens on a loopback port (`"url":"http://127.0.0.1:41817"`) and `opened` has no `socketPath`. Each `call` is one of `recorder.record`, `tools.list`, `tools.check`, `tools.call`, `approvals.request`, `approvals.remote-decision` and `secrets.get`, with the port's arguments (`approvals.remote-decision` takes `{ callId, approved, source: "remote-device" }` and tells Studio that a person decided a waiting approval on a paired phone; Studio answers `{ status }`, one of `decided`, `unknown` or `already-decided`); Studio answers it with `POST /v1/bridge/answer` and `{ bridge, call, result }` or `{ bridge, call, error }`. A `cancel` means the bridge stopped waiting (the program went away), so Studio can stop the tool call or withdraw the approval. The host checks each answer against the port's shape, and asks only for the secrets the run's `providers` name. A bridge is named by a random id the host makes, like a session, because call ids (`1`, `2`, …) repeat from bridge to bridge.

Studio must answer `recorder.record`, `tools.list`, `tools.check`, `approvals.remote-decision` and `secrets.get` within 30 seconds, or the host sends a `cancel` and the bridge's request fails, so a Studio that hangs can't hold it forever. `tools.call` and `approvals.request` have no limit, because a tool's run and a person's approval rightly take long. A call fails too when Studio answers it with an error, or when the stream ends (Studio crashed or reloaded) before it answers.

When the bridge fails a request for a reason it doesn't name to the program, which is told "The run log has the details.", the host sends Studio a `recorder.record` call with `{"type":"bridge.failed","agent","kind","message"}`, so the run log has them; the message never holds the run token, and Studio takes it out again if it does. Nor does it hold a key Studio gave the bridge through `secrets.get`: the host removes every such value from the message first, and Studio removes it again before the run log records it (`agent-host.bridge-key-scrub`). When Studio doesn't take that call, the host writes the failure to its standard error.

When the agent's file says `asks: in-sandbox`, Studio adds `"asks":"in-sandbox","harness":"claude-code"` to the open body, and the host answers the program's own calls itself while the run's session is fenced (`agent-host.sandboxed-asks`): an edit or read in the working folder, a `Bash` command and `TodoWrite` are approved without an `approvals.request`, and each goes to Studio first as a `recorder.record` call with `{"type":"harness.allowed","agent","tool","detail","rule":"asks-in-sandbox","waitedMs"}`, where `waitedMs` is how long, in whole milliseconds, the host took from getting the ask to its answer (`harness-host.allowed-waited`; Studio takes the event without it too). The fence is the one the host's own session proved, the session `POST /v1/harnesses/runs/start` starts the run in, never one Studio names, and before a run starts on the bridge every call goes to Studio. The `detail`, the path or command, loses the keys Studio gave the bridge, as a `bridge.failed`'s message does, and Studio takes the run token and those keys out again (`agent-host-client.bridge-allowed`). Every other call goes to Studio's `approvals.request` as before.

The bridge closes on `POST /v1/bridge/close`, which waits until its last events are recorded and then ends the stream; when Studio goes away, which ends the stream; and when the host stops.

Each bridge listens on a port or socket of its own, so the host keeps at most 64 bridges open, counting those still opening and those still closing; past that, opening one answers `429 too_many_bridges` before any stream starts.

## The harnesses over loopback

Studio gives the engine a stand-in `Harness` for each one the host lists, and the host runs the real one inside a sandbox session and with a bridge Studio opened here first. Studio starts a run with `{ harness, task, session, bridge }`, naming the session and the bridge by their ids, so the bridge's token never travels again. The answer stays open as a stream:

```
{"type":"started","run":"<id>"}
{"type":"event","event":{"type":"tool.called",...}}
{"type":"event","event":{"type":"agent.finished",...}}
{"type":"finished"}
```

A run that fails or is cancelled ends with `{"type":"failed","message"}` instead of `finished`. A harness, session or bridge the host doesn't have gets `404 unknown_harness`, `unknown_session` or `unknown_bridge`. When Studio goes away the run is cancelled, and when the host stops it cancels every run before it closes the sessions.

The port's `environment` has no route: the engine asks for it without waiting, and it only reads its arguments, so Studio calls the adapter's own function with the bridge's address and token from `/v1/bridge/open`.

## Building a harness profile

`POST /v1/harnesses/profile` is the engine's `HarnessProfileBuilder` run next to the sandbox (HAL-10849): it reads folders on disk and resolves links, which Studio's page can't. The body is `{ workspace, agent: { runId, hubId, agentId, harness, workingFolder, allowedSites, filesFolder }, bridge, instructionsFolder }`, with the bridge by the id `POST /v1/bridge/open` gave. `instructionsFolder` is the absolute path of the run's folder of pinned instruction files (`AGENTS.md` and `skills/<id>/SKILL.md`) as `POST /v1/harnesses/instructions` answered it, or `null` when the agent has none; the profile opens it read-only. The host builds the profile with `HarnessProfiles` for a `workspace` the launcher named (`--sweep-root`; compared by real path) and answers it as the engine's `HarnessProfile`, which Studio opens a session with.

- **What Studio decides, and what it doesn't.** Studio gives the agent's working folder and sites from its file, and the run's proposal folder. Halonic's data folder (the profile folder), the home folder and the program's variables are the host's own; a body with any other field is `400`. The bridge's token never leaves the host, and is not in the answer.
- **Only the host's own profiles open.** `POST /v1/sandbox/sessions/open` opens a session only for a profile built here whose session hasn't opened yet, so each opens one session. The engine may add the harness's own variables to `env` (as `addHarnessEnvironment` does), but every other field, and every variable the host set, must be as built; anything else is `403 profile_not_built`. A host without a profile folder builds no profile and opens no session. The instructions folder must be one the host made and hasn't removed, or the answer is `404 unknown_instructions`.
- **A refused profile.** A working folder that leaves the workspace or is in a protected folder, a proposal folder outside Halonic's data folder, a folder of the run in a denied one and the like are `422 profile_refused` with the builder's own reason.
- **Temp folders.** Each profile gets its own fresh, private temp folder in the workspace's folder of the profile. The host removes it when the session opened with that profile closes, and removes no other folder. A host that crashed leaves its open sessions' folders; clearing them is a follow-up.
- **Windows.** The host does not yet find where a harness is installed there, so a profile is `422 profile_refused` on Windows, as the CLI refuses a harness run there.

## Signing an agent in

An agent that uses a Claude Code or Codex subscription signs in once, in its own settings folder (HAL-5395). `POST /v1/harnesses/sign-in` with `{ harness, settingsFolder }` opens a terminal the person can see (below), running the harness's own `signIn`: `claude auth login` with `CLAUDE_CONFIG_DIR`, or `codex login` with `CODEX_HOME`, set to that folder. The person signs in there as usual. The host only opens the window: it never reads, copies or waits for the sign-in, so Studio runs `detect` again when the person chooses Check again.

- `settingsFolder` must be an absolute path (`400 body_invalid` otherwise).
- The program is found on the host's `PATH`, as `detect` finds it. When it isn't there, or no window could open, the answer is `{ opened: false, reason, command }`: `command` is the sign-in to type by hand, in PowerShell on Windows (`New-Item -ItemType Directory -Force -Path '<folder>' | Out-Null; $env:CLAUDE_CONFIG_DIR = '<folder>'; claude auth login`) and in `sh` elsewhere (`mkdir -p -m 700 '<folder>' && CLAUDE_CONFIG_DIR='<folder>' claude auth login`), from `signInCommandText` in `@halonicjs/ports`, so `halonic doctor` shows the same command. It makes the folder first, because Codex won't sign in to a folder that isn't there; Studio's folder is there already, made by `POST /v1/harnesses/settings-folder`, but `halonic doctor` names one that may not be.
- A harness without a sign-in of its own gets `422 no_sign_in`, and a command the terminal refuses (a folder under a skill's `scripts/`) `422 sign_in_refused`.

Studio learns the agent's settings folder from `POST /v1/harnesses/settings-folder` (HAL-6351): the folder a run of that agent uses, `harness-settings/<agentId>/<harnessId>` in the workspace's folder of the profile, made private. It passes that folder to `detect`, so the Harness page shows whether this agent is signed in, and to the sign-in.

## Opening a terminal the person can see

`openTerminal` (`src/terminal/open-terminal.ts`) opens a new terminal window that runs one program, so the person answers it themselves. It is for a harness program's own sign-in for one agent, such as `claude auth login` with `CLAUDE_CONFIG_DIR` set to that agent's settings folder. It takes the program's absolute path, plain-word arguments and the variables to add to the person's environment:

- **Windows:** `cmd.exe` from the Windows folder runs `start`, which opens a new console window. The variables travel in the environment, never on the command line, and a program path with a `%` in it isn't run, because `cmd.exe` would expand it.
- **macOS:** it writes a `.command` file to a new private temp folder and opens it with `open`, so the person's chosen terminal runs it. The variables are quoted for `sh` there.
- **Linux:** it uses the first of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xfce4-terminal` and `xterm` it finds on the `PATH`, with the variables in its environment.

It answers `{ opened: false, reason }` when no window could open: no terminal or desktop session, or a start that failed. The caller then shows the command to run by hand. It throws, as a mistake in the caller, for a program that isn't an absolute path, an argument that isn't a plain word, a variable name that isn't one, and a program or variable under a skill's `scripts/` folder.

## Proposal folders

`POST /v1/proposals/*` is the engine's `RunProposalFolders` run next to the sandbox (HAL-10849): a worktree or a copy is made on disk and git needs Node, which Studio's page doesn't have. The host keeps worktrees, copies and proposal records in Halonic's data folder for a `workspace` the launcher named (`--sweep-root`; compared by real path), never in the workspace. A run with a live version gets a git worktree at its commit; a run that reads the saved files gets a plain copy, so a workspace without git works until a run needs a worktree. Git starts at the first such run, and `start` starts none for a workspace with nothing kept. A body with any other field is `400`.

Program copies: `POST /v1/program-copies/start | open | release` is where Studio's window starts a live run's programs (HAL-16260): `open` with `{ workspace, commit }` answers `{ path }` of a git worktree at the commit, made with `@halonicjs/adapter-program-copies-node` and the same hardened git as the CLI, so a saved change, `.env` or `node_modules` never reaches the run's programs. `commit` must be a full hex object id. The copies go in the workspace's `agent-host-program-copies` folder in the profile, beside the CLI's `program-copies` and never inside it: the host can't tell whether it holds the engine lock, and each side sweeps only its own folder. `start` stops the workspace's connectors first, then removes the copies the host holds and those a stopped host left. `release` with `{ workspace, path }` removes only a copy the host holds for that workspace, compared as a real path; any other path is `404` and nothing is removed. A workspace the launcher didn't name is `404 unknown_workspace`, and a copy that can't be made is `422 program_copy_refused`, never the saved folder. `POST /v1/connectors/open` takes a held copy as its `workspaceRoot`: the trust grant is checked on the record of the workspace it came from, and working folders must be inside the copy. That start runs in the workspace's turn, so a `start` or `release` of its copies waits until the connector is in the table, and a `start` then closes it before it removes the copy. When the host stops, the copies go after the connectors and sessions, then their git.

Temp folders of profiles: a profile whose session doesn't open within ten minutes (its run was cancelled in between, say) has its temp folder removed too.
