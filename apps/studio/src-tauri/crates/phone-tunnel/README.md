# halonic-phone-tunnel

The phone's tunnel service (tunnel D6, HAL-15157): what the Android shell's phone tunnel commands call. It runs a pairing with `halonic-tunnel`, keeps the computers the person allowed in `halonic-device-keys`' list with the phone's own key for each, and connects to them. Plain Rust with no Tauri types; the shell's `phone_tunnel` module wraps it.

**Keys stay here.** The page gets only the answers in `answers`, the `PageStatus` the shell passes on and the text of gateway messages: the check code, computer names and ids, endpoints, times, states and session generations. Never a private key, a session key, the pairing code or its psk. A computer's id is the hex of its static public key when the phone first paired with it.

- `PhoneTunnel::pair_start`: reads the page's `PairingStart` again (the QR code's host key, the code, the endpoints; `start`), asks Android's local network question when an endpoint is on the Wi-Fi, ends any other pairing, and runs pairing messages 1 to 3. It answers the computer's name and the check code, or a `Problem`. The wait for the computer's Allow starts at once in the same task, so the connection never sits idle and the 130 seconds count from message 3.
- `pair_wait`: collects that wait. Once allowed, the computer is listed with the phone's new key (pairing again keeps its id), any connection under an earlier key ends, and it answers the computer. `pair_cancel` ends the pairing, which ends it on the computer too; a waiting `pair_wait` answers `code-ended`. One pairing runs at a time.
- `computers`, `forget`: the listed computers, Removed ones included; Forget ends the connection, then wipes the key and the details, and ends any connection started meanwhile.
- `connect`, `disconnect`: one connection per computer, at the first of its endpoints that opens. Connecting again answers `connecting`, and makes one that waits to reconnect try at once ("Try now"). The list follows the connection: connected, can't confirm (nothing cleared), and Removed, which wipes the key and the pin **before** the page hears of it. Only while the computer is still kept under the key that connection used: after a Pair again, an earlier connection changes nothing, even a note already waiting for the list. While reconnecting, the status says when the next try starts (`nextTryAtMs`).
- `send`, `end_session` (D7a, HAL-15177): the page's gateway messages. Each session that opens gets a generation, counted across every computer and never given again, and the page hears `session_opened` and then each host message as text, in order. `send` seals a message only into the session of the computer and generation the page names, after `check_message`: at most `GATEWAY_MAX_MESSAGE_BYTES` (65,519) bytes of UTF-8, counted before parsing, and exactly one JSON object, with no key twice, whose `type` is from `PHONE_MESSAGE_TYPES` and whose other keys are exactly that message's, so the shell and the host's `JSON.parse` can't read one message two ways. An `answer-approval` goes out only after `TunnelHost::confirm_owner` passed for its `decision` (HAL-15194, board decision 4b); a phone without an owner check answers through `confirm_with(None, ..)`, which never passes. A `msg-answer` asks it too, unless a pass for an earlier `msg-answer` less than `ANSWER_WINDOW` (5 minutes) ago still covers it and `TunnelHost::times_away` hasn't changed since (requirement `phone-answer-confirm`, board option P3); the pass is kept in memory only. Anything else is a `SendRefusal` (`not-open`, `too-large`, `not-allowed`, `not-confirmed`), nothing goes out, and the session stays open. There is no queue and no retry; the tunnel crate's numbered sessions make sure a message for an ended session never goes out on the next. `end_session` drops a session the page refuses, and the phone reconnects without the backoff starting again; a host message that isn't UTF-8 ends its session the same way.
- `TunnelHost`: what the service needs from the shell. Android's local network question, passing a status, a session's opening and its messages on to the page (only while the window is on the app's own page, H1 on HAL-15181), and the shell log for failures no page waits for, which never holds a message's text.
- `Problem`: every failure as a typed `kind` (`wrong-code` with `triesLeft`, `code-ended`, `code-used`, `rate-limited`, `denied`, `timed-out`, `handshake-failed`, `cant-reach` with its `reason`, `no-local-network`, `unreadable` (the computer's answer), `bad-start` (a code or key from the page that isn't one), `not-paired`, `key-unreadable`, `keys-unavailable`), never a raw message.

The shell's `tunnel_send` and `tunnel_end_session` commands come with the next part of D7a. TLS endpoints need the shell to give a `Dialer` with the platform verifier; until it does, they can't be reached.

The tests run the service against the tunnel crate's fake host (`../tunnel/tests/support`) on loopback, with the fake key wrapper. The requirements in `requirements/` are drafts until the trace check reads `cargo test` results; until then each test's name starts with the last part of the requirement it proves.
