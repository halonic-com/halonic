# halonic

The `halonic` command-line tool. It uses the same core packages as the Studio, and every command
lives in its own folder.

- **Layer:** apps
- **Owner:** liam
- **Public API:** `halonic` (`runCli`, the command types and the exit codes, so tests and the parity
  harness can run the CLI in-process)

## Commands

| Command | What it does |
| --- | --- |
| `halonic doctor` | checks this computer's sandbox (the Sandbox line, when ready, names the kind: "ready · bubblewrap", "ready · Seatbelt" or "ready · Sandbox for Windows") and disk, and a workspace's models and the secrets its used connectors, its providers without a key check, its enabled webhook routines and the provider key `halonic run` gives a Claude Code or Codex agent in the sandbox need (✕ Secrets, one line per missing secret with what uses it and `halonic secret set <name>`, exit 1; ! when the store can't be read); `--dir <folder>` picks the workspace. It asks a local model server on this computer (`localhost`, `127.0.0.0/8`, `::1`) always, and one at any other address only once the workspace is trusted here; before that, such a server shows as not answering and nothing is sent to it. Under WSL the Workspace line is ! when the workspace is on a Windows drive (`/mnt/c`), and a Node.js line (!, only when there is a problem) says when this is Windows' Node.js in a WSL folder, or the `pnpm` on the `PATH` is Windows' one (`src/wsl.ts`). A Network line (!, only when there is a problem) says when the proxy setting `HTTPS_PROXY` or `https_proxy` is a proxy of another kind than `http://`, such as `https://` or `socks5://`, or one Halonic can't use, with the reason. It is read without any network call, and `doctor` still exits 0 for it (`src/doctor-network.ts`). When the workspace and the profile folder overlap, as every other command refuses (`profile-in-workspace`, `workspace-in-profile`), `doctor` instead prints a Profile line ✕ first, with the same reason and fix, leaves the workspace's own lines out, and exits 1 (`src/profile-place.ts`). A Plugins line names each plugin that a connector an agent uses needs and that isn't added on this computer (✕, with the connector and a close plugin id when there is one, exit 1), or that is off or can't be read (!, with `halonic trust --plugin <id>` or `halonic plugin remove <id>`), or the plugins folder when you may not read it (!, with the folder and `chmod 700 <folder>`), the same states `halonic tools review` gives; the profile's plugins are read only when an agent uses a plugin's connector (`src/doctor-plugins.ts`). A check that doesn't answer in 5 seconds shows as ! with "didn't answer in 5 seconds", and the other lines still show |
| `halonic extract <hub> <new-folder>` | moves one hub, with the shared items it uses, into a new workspace in an empty `new-folder`; the workspace it comes from (`--dir`) is left as it is. `--dry-run` lists the files and writes nothing. Exit 4 for an unknown hub, 5 when the workspace has errors or the folder isn't empty |
| `halonic init [folder]` | lays out a new workspace in `folder`, or in the current folder when it's empty, with a Default hub and the test model (`models.yaml` alias `default`, `providers/mock.yaml`) but no agents or workflows; it never writes into a folder with files in it (exit 5); `--example acme` copies the Acme example instead, into `./acme` when no folder is named. `--dir <folder>` is wrong usage (exit 2), and the fix is the same command line with the folder first, such as "Give the folder as the first argument: halonic init x --example acme." |
| `halonic plugin add <folder or git address>[@commit]` | copies a plugin into this computer's profile, leaving out `.git`, `.studio`, `.env*` and the home-folder paths the sandbox denies (such as `.ssh` and `.aws`) at any depth, and naming the latter on a line `! Not copied, because they're private: …`; it shows its trust check and asks "Trust Weather and turn it on?", or for a plugin with a backend whose code can't run in the sandbox on this computer "Trust Weather?", after "! Trusting Weather won't turn it on: it stays off on this computer until you allow plugins and integrations to run without the sandbox.", the reason and its fix, and where to allow it in the desktop app (the same lines come before the command to run when there's no terminal, and with the refusal of a `--fingerprint` that doesn't match); `--yes --fingerprint <fingerprint>` without a question. A git address (`https://`, `ssh://`, `user@host:path`) is checked before git starts and one commit of it is exported to a temporary folder, which is deleted after; without `@commit` it uses the latest on the default branch and says how to pin it; `@` also takes a branch or tag. The check's folder line is followed by "Copied from <source>", where it came from as `plugin list` writes it. Once copied, the plugin stays added whatever the answer: No, no terminal or a `--fingerprint` that doesn't match leaves it off (exit 3). A yes for a plugin with a backend whose code can't run in the sandbox on this computer says "! Added Weather 1.2.0. It's trusted, but off on this computer until you allow plugins and integrations to run without the sandbox.", the reason and its fix, a dim "More:" line with the sandbox guide's section, and "Or allow this in the Halonic desktop app: Settings › Plugins › Weather › Review. The halonic command runs plugin code only in the sandbox." (exit 0; `--json` `offOnThisComputer` gives the reason's code, such as `container`); the command never runs plugin code without the sandbox. Exit 2 for a source it can't use, 5 when the plugin is already added. With `--update`, a plugin that is already added is replaced by the new copy and keeps its settings and secrets: changed files show the check and ask again ("✓ Updated Weather 1.2.0. It's on."), unchanged ones ask nothing ("✓ Updated Weather 1.2.0. Its files are the ones you trusted, so it's still on."), and `--json` adds `"updated": true`; when the plugin was added from another folder or git address, "! Updating from a different source: <old> → <new>. Its settings, secrets and sign-ins carry over to this copy." comes first, and "! Files changed since the copy it replaces: changed backend/index.js; new backend/extra.js." names the files that differ from the copy it replaced (at most 10, then "and N more"); No or no terminal says it in `plugin list`'s words ("Weather is updated but off: it's changed since you trusted it. …"); a plugin that isn't added yet is added as without it. An `https://` git address with a user name in it is refused (exit 2), so no token given that way is kept or shown. |
| `halonic plugin list` | lists the plugins in this computer's profile (`halonic plugin` alone does the same), one line each with four columns: name, version, where it was added from (a git address without the scheme and `.git`, then `@` and the first seven characters of the commit, or for a folder "copied from" its path with the home folder written `~` and the day it was added or updated, such as "copied from ~/weather on 20 Nov") and whether it is on (✓ on, ! not trusted yet, ! changed since you trusted it, ! off on this computer for a trusted plugin with a backend whose code can't run in the sandbox here, with the reason, the "More:" line and "Or allow this in the Halonic desktop app: Settings › Plugins › *Name* › Review. …" under it, or ✕ for a folder that can't be read or checked, which doesn't stop the others); under a plugin with programs, a line says whether they run on this computer ("Programs: In the agent sandbox, in its own empty folder", or with ! "Programs: Doesn't start on this computer: the sandbox can't start here"); under a plugin copied from a folder whose files changed since, "! The folder changed since it was copied. To use your changes, run: halonic plugin add ~/weather --update"; `--json` gives each plugin's id, name, version, status, source, `addedAt`, `programsRun`, `offOnThisComputer` (the reason's code, such as `container`, or `null`) and `sourceChanged` (`true` or `false` for a folder it can read, else `null`); a trusted plugin that is off on this computer keeps `"status": "on"`, because `status` says it is trusted, and `offOnThisComputer` says whether it can run here, so a script checks both before it takes a plugin as running. It writes nothing and needs no trust, and exits 0 when it lists, empty or not; a plugins folder you may not read is refused with its fix, such as "Run chmod 700 <folder>, then run again." (exit 7); a file in the profile's `plugin-records` you may not open is refused the same way, with `chmod 600 <file>`, and a damaged one with its line and "Delete line <n> from it, or delete the file, then run again." (exit 9), as `halonic plugin remove` refuses them (`src/plugin-record-store.ts`) |
| `halonic routines` | lists the workspace's routines in the order of their files, one line each: the name, its trigger in words, its next run ("Next 16 Nov 09:00", "Next tomorrow 09:00", "Next 14:00" for today, "Off", "No set time", or "✕ Can't start" for a routine whose file has errors, even when it is on, or for a webhook routine that is on and that `halonic serve` says can't start (its secret isn't set or has a name Halonic keeps, a trigger value a web request has no value for, or it starts an agent), with `nextRun: null` in `--json`, where the document then also has `"ok": false`; also for a routine that starts an agent on its own, which Halonic can't run yet, with `startsAgent: true` in `--json` and a line under the list saying why and what to do, without changing the exit code; or "! Paused until trusted" for one that is on in a workspace that isn't trusted here, as `routines watch` would refuse it, under a first line naming `halonic trust`, and `trusted: false` in `--json`) and its last run ("Never ran" when it hasn't); `--json` gives every routine `problems`, how many errors its file has (`0` for such a webhook routine too, though it can't start); a first line "! 3 routines can't start. The lines under the list say why." counts the routines with file errors or an agent on its own, and each gets its reason under the list, its file's errors first ("! Friday digest can't start until its file is fixed · halonic validate"), a line after it "! 2 routines can't start on a web request · halonic serve --dir ." counts those webhook routines (a routine with file errors is counted once, under `validate`), and the command then exits 1; a routine whose last commit has errors that its saved file no longer has is counted on a line of its own, "! 1 routine can't start until its fix is committed", since `validate` reads the saved file; `halonic routines list` does the same; the name is followed by the hub's id when routines come from more than one hub, so two of the same name can be told apart; for a routine with changes that aren't live yet, the trigger, the Next column and `--json`'s `nextRun` and `timeZone` show the live version (the one `routines watch` runs), the name and On or Off come from the saved file, and a line under the list says "! Weekly report has changes that aren't live yet. It runs as last committed until you commit them or make them live in Halonic Studio." (when the saved changes have errors: "! Weekly report has changes that aren't live yet, with errors. It runs as last committed. See the errors with halonic validate --dir ..", and the row still shows the committed version, exit 0); a routine that is on but was never committed, in a folder with git history, shows "Not live yet" in the Next column (`nextRun: null`) and a line "! Hourly ping isn't live yet, so it doesn't run. Commit it to start it."; `--json` gives each routine `liveState` (`live`, `not-live` or `never-live`) and `savedProblems`; a last line says "Routines start on time only while this workspace is open in Halonic Studio, or while `halonic serve` or `halonic routines watch` is running."; `--json`, `--dir <folder>`. It starts nothing, writes nothing and needs no trust. A repository Halonic doesn't allow stops it with its reason and fix, exit 7, as for `run`. |
| `halonic routines watch` | in the foreground, starts the routines when they are due and moves on the runs that wait for a time, until Ctrl C ("Stopped.", exit 130), SIGTERM (exit 143) or a closed terminal (SIGHUP, exit 129); `--dir <folder>`. Each routine run reads the live version at the time it is due, as the Studio's scheduler does, or the saved files with history off; like `run`, it refuses a workspace with history but nothing live yet, or whose git can't start. It checks trust and the sandbox first, as `run` does: exit 3 for a workspace that isn't trusted here, unless its runs can only reach the test model. A version made while it watches is checked the same way before a run starts from it. Its first line, "Watching 1 routine in Acme. Stop with Ctrl C.", comes before any run's line, also for runs the catch-up tick starts. A routine whose own file has errors gets "✕ Friday digest can't start until its file is fixed · halonic validate" before that first line, with its name, or its id when the file doesn't load at all (an unknown field, say); the watch leaves it out, and doesn't count it in "Watching N routines", until its file is fixed; the next tick then prints "✓ Friday digest can start now" and starts it as usual, and the others run on time. It also leaves out a routine that starts an agent on its own, with the list's "✕ Daily digest can't start: Halonic can't run an agent on its own yet, …", and one whose workflow has an agent that runs in Claude Code or Codex, which it can't start yet, with "✕ Daily notes can't start: Coder runs in Claude Code, which routines can't start yet. …". Routines that are on but not live yet, which it doesn't run, are counted before that first line: "! 3 routines aren't live yet, so this watch doesn't run them. To start them, commit them or make them live in Halonic Studio." An error in any other file stops the watch with exit 2, as `run` does. Then it prints one line per run it starts and a ✕ line for one that didn't start. A run whose step fails three times gets "✕ Hourly follow-up got stuck · run 09d9f0 · see why with --debug" and the watch keeps going while the engine retries that step. Three failed ticks or wake-ups in a row stop it with the last error, and one that works starts that count again. If it is paused so long that it loses its hold on the workspace, such as while the computer sleeps, it stops with "✕ Couldn't watch the routines in acme: the engine stopped: this command was paused too long, such as while the computer slept, and lost its hold on this workspace." and "Run the command again.", exit 5. A repository Halonic doesn't allow stops it with its reason and fix, exit 7, as for `run`. |
| `halonic models allow-address <key-name> <address>` | adds one address to the addresses a stored key may be sent to, keeping the others; only the scheme, host and port of what you type are kept. Exit 0 also when the address was already allowed; 2 for an address that isn't `https://` or `http://` or holds a user name or password; 4 for a key that isn't stored; 8 when the key has the most addresses (8); 9 when the profile's secrets file can't be read or written. It refuses to run inside a run (exit 7), where the run marker `HALONIC_RUN_TOKEN` is set; this is a second layer, the sandbox is the boundary |
| `halonic serve` | in the foreground, serves the workspace through the secure server until Ctrl C (exit 130) or SIGTERM (exit 143); `--dir <folder>`, `--port <port>` (4747 by default; 0 lets the system choose) and `--network`. It refuses a workspace that isn't trusted here, or changed since, and serves nothing (exit 3). It listens on this computer only; `--network` also opens it on the home network and needs a sign-in password, set with `halonic secret set serve-password`. `--public-origin https://<host>` serves it behind a proxy on this computer: it needs that password too (or it doesn't start), can't go with `--network`, listens on `127.0.0.1` only, answers only to that host name (never `localhost` or `127.0.0.1`), treats every request as HTTPS without reading `X-Forwarded-*`, and its first line names that address. Setting the password again ends every sign-in, and `secret set` says so. Its first line, "Serving Acme at http://localhost:4747. Stop with Ctrl C.", is followed by a line naming that command when no password is set, and by a line naming `pnpm --filter @halonicjs/app-studio build` when the Studio page it serves from `apps/studio/dist/studio` isn't built, or is older than its code, as after a `git pull`. Each webhook routine that is on gets a line "Friday digest starts on a web request at <address>"; when it can't start, the line says only "Friday digest has the web address <address>", and a ✕ line under it says why: its secret isn't set (naming `halonic secret set <name>`), its secret's name belongs to Halonic or a plugin, it has a trigger value a web request has no value for (validate's reason), or it starts an agent ("✕ Friday digest can't start: Halonic can't run an agent on its own yet, only as a step in a workflow. Make a workflow with the agent as a step, then start that."). While it serves, it prints "✓ Weekly report started on a web request · run 17c592" for a started run, "Weekly report skipped a web request: its previous run is still going (overlap: skip)." for a skipped one, "✕ Weekly report didn't start on a web request: <reason>" for a 400 or a 501, and for a 500 "✕ Weekly report didn't start on a web request: Halonic ran into a problem it can't explain yet." with a second line to start it again with `--debug` and report it; a 401 prints nothing. A signed-in browser can save a provider key to this computer's secrets file, the one runs read (`/api/secrets/<name>`), and test and save a model choice (`/api/model-choice/…`): Continue writes only the choice files it changes (`models.yaml`, `workspace.yaml`, the one `providers/<name>.yaml`) and commits only those, as "Save the model picked through halonic serve", leaving every other file as it was; when one of them has changes that aren't committed it saves nothing and refuses with "Couldn't save: models.yaml has changes that aren't committed. Commit or undo them, then try again." A browser never trusts the workspace: when the choice adds a provider, trust it again on this computer. A port in use exits 5 and suggests the next port. The server asks the read-only trust gate again before every request that starts a run. While it serves, the routines on a schedule or a signal start as `routines watch` starts them, each as a normal run, and a failed run doesn't stop the next one; a signed-in owner pauses or resumes them with `PUT /api/routines/pause` and the body `{"paused": true}` or `{"paused": false}`, and reads whether they are paused, the runs going and the next start at `GET /api/routines/health` (`server.routines`). The served Inbox names each agent as its file in the live version does. An agent in Claude Code or Codex runs on this computer, in the sandbox, from the live version; a start can't name its harness, placement or sandbox (400). If it is paused so long that it loses its hold on the workspace, such as while the computer sleeps, it stops with "✕ Couldn't serve acme: the engine stopped: this command was paused too long, such as while the computer slept, and lost its hold on this workspace." and "Run the command again.", exit 5. A repository Halonic doesn't allow stops it with its reason and fix, exit 7, as for `run`. |
| `halonic deploy [<deployment>] [--plan [--exit-code]] [--yes] [--dir <folder>]` | deploys the workspace's last commit to your Cloudflare account, asking `Deploy? [y/N]` first when something is new; `--yes` answers it; Ctrl C says which step it stopped after and which version is still live. `--plan` shows what a deploy would do and changes nothing; with `--exit-code` it exits non-zero when something would change. With no name in a workspace with no deployments it says there are none and how to add one in `deployments.yaml` |
| `halonic deploy status <deployment>` | shows the address, live version, the Halonic version it runs, whether it answers, how many runs it has and the version a rollback would go back to |
| `halonic google allow-sending <connector> on\|off` | switches sending on or off for one Google connector of the workspace (`--dir <folder>`). Sending stays off until a person runs this with `on`; `halonic run`, `halonic runs send`, `halonic serve` and `halonic routines watch` read the saved choice each time they meet a `send` call, so a change applies to the next run; the choice is kept in the profile's `connections` folder, never in the workspace. It prints "✓ Sending is on for mailbox in Acme.", also when nothing changed, and adds `connection`, `workspace` and `allowSending` to `--json`. A connector the workspace doesn't have exits 4, a connector that isn't a Google one exits 2, and nothing is saved |
| `halonic secret remove <name>` | removes the secret `<name>` and prints "✓ Removed <name>." (exit 0). A name that isn't saved changes nothing and prints "<name> isn't set, so nothing changed. To see the secrets that are set, run halonic secret list." (exit 0; `--json` says `"removed": false`). When it isn't saved but the `HALONIC_SECRET_<NAME>` variable holds a value, it prints "No secret <name> is saved. Nothing changed." and a line saying runs still read the secret from that variable and that unsetting it removes it. A name Halonic keeps for itself, such as a sign-in token's, is refused with its reason (exit 2); no name, or more than one, is wrong usage (exit 2) (`cli.commands.secret.remove`) |
| `halonic google reset` | the way out when the profile's token key is gone while secrets it sealed remain: after asking (or with `--yes`) it removes the Google accounts set up on this computer, with their sealed secrets, and the integrations' saved sign-ins, then prints "✓ Removed."; the next Google setup makes a new key. The key and the other secrets stay. With nothing to remove it asks nothing, says "Nothing to remove: this computer has no Google accounts or saved sign-ins." and exits 0, with or without a terminal. No exits 1; with something to remove and no terminal or `--yes`, nothing is removed (exit 2). A folder it removes that it can't read stops it before it asks: it names the folder, removes nothing and exits 7 |
| `halonic run <workflow>` | starts a workflow (`hub/workflow` when several hubs have it) in this computer's engine and follows it step by step, printing each step's line as the step ends; `--input <file or JSON>`, `--event <event>` (answers a wait, once per wait, in order), `--harness <harness>` (the harness all agents in the run use instead of their own: `halonic`, `claude-code` or `codex`), `--dir <folder>`. Every line the CLI draws shows control and bidi characters in outside text (names, engine or server messages) as `\u` codes, such as `\u001b`; `--json` keeps them as written (`cli.outside-text-escaped`). `--json` gives one document, `run` and `events` (oldest first); `--json --follow` gives JSON Lines instead, one `{ outputVersion, event }` line for each event as it happens, then one last line, `{ outputVersion, ok, run }` or `{ outputVersion, ok: false, error }` (`cli.json-lines`). stdout holds only those lines, stderr stays empty except for `--debug` lines, and the exit codes don't change. `--follow` without `--json` is a usage error (exit 2). `--input` takes a JSON object; a missing file, a folder, a file it can't read or JSON that isn't an object is refused with a reason (exit 2). An `--event` the step doesn't take, or for a run that is gone, is refused in `runs send`'s words; a wait someone else answered first (such as in Studio) is no error, and if the run ended before it took the last `--event`s, one dim line says so ("! Didn't use --event reject: the run ended first."). It refuses a workspace that isn't trusted here (exit 3) unless the run can only reach the test model (every provider `mock`, no connector, no local integration, no agent in a harness; the rule is `reachesOnlyTheTestModel` in `@halonicjs/workspace`, which Studio can use too). For a workflow with an agent in a harness, the sandbox is checked before that check (below), so a run the sandbox can't start shows no trust check. A workspace whose git repository Halonic won't read (a linked worktree or a submodule, a repository that reads objects from outside its folder, or a config key such as `include.path`) is refused with the reason and a fix (exit 7). `runs send`, `routines watch`, `routines list` and `serve` do the same (`cli.repository-refused`). When a run ends refused because nobody trusted an agent's instructions, and someone can answer (a terminal, no `CI`, no `--json`), it shows the files the run's check saw and their fingerprint, as `halonic trust instructions` does, and asks "Trust coder's instructions on this computer? [y/N]". On yes it trusts exactly what the check saw, says "✓ coder's instructions are trusted on this computer. Starting the run again." and starts the run again once; the refused run stays in the log. On No, or with nobody to ask (CI, `--json`, a routine, `serve`), it trusts nothing and ends with the refusal's two lines, "… coder didn't start, because its instructions aren't trusted on this computer yet." (or "… changed since they were trusted on this computer.") and "Review and trust them with halonic trust instructions coder, then run again." (exit 1). No option of `run` trusts instructions without a person's answer. When a connector doesn't start, the run goes on without its tools and warns on stderr, once for each connector, also with `--json`: "! handbook didn't start, so its tools are off in this run." with the cause and fix under it, or "… couldn't list its tools …" and the `halonic tools review` command for another cause (for an integration's connector, `halonic doctor`, which checks the sandbox and trust it needs to start). For a part of a plugin that can't start, the warning names the part ("! The program lister of the plugin files didn't start, so its tools are off in this run.") with the reason and fix, and the log records it as `connector.part-off`; that connector gets no second warning. For a plugin's connector whose tools couldn't be listed, the warning says that the sandbox its plugin runs in can't start, or names a plugin that isn't added (and the added plugin whose id is close) or can't be read, in `tools review`'s words (`cli.run-plugin-connector-warning`). Such an agent writes only in its run's proposal folder: when the run ends with changes, a last line says so and names `halonic proposals show <run-id>`, and `--json` gives them as `proposal`. Nothing in your files changes until you accept. Under a step that ended, a failed tool call gets the dim line `runs show` prints for it, such as "  Didn't work: the tool search_pages broke off without an answer, so it may or may not have done its work.", right after the step's line, and the result repeats it (`cli.run-live-failed-call`). When it waits for you, the wait's body shows under its title and before the "Answer with:" line; for the Support reply workflow that is the reply it asks about, under "! Waiting for you: Approve this reply?", then "Approving finishes the run. Nothing is sent." (other workflows show their own text) (the wait's body, `waitingFor.body` in `--json`; `cli.run`). Exit 0 when the run finished or waits for you, 8 when its budget stopped it, 1 when it failed otherwise; Ctrl C, SIGTERM or a closed terminal (SIGHUP) stops following it and says it was cancelled, or, when the engine couldn't cancel it, that it "wasn't cancelled, only no longer followed, so it may go on" and points to `halonic runs show`. A run that failed because the secrets file can't be read by your user account (here and in `runs show`) says so on line 1, gives the fix on line 2 (`chmod 600 <file>`, `sudo chown` back to you and then `chmod 600`, or the file's Properties), with no bug report line, and `run` exits 7 (`denied`), as `secret list` does; `--json` carries the cause, the file and the fix in `cause` (`cli.run-secrets-unreadable`). A run that failed with `sandbox-not-ready` (here and in `runs show`) is worded from its `sandboxReason` code alone: the sandbox can't start on this computer, with the same reason and fix as a refused run (`cli.run-failed-sandbox`). With `--debug`, a retry of a failing engine timer shows on stderr ("try 2 of 3, retrying"); the third failure of the same timer stops the command with its error |
| `halonic runs` | lists the workspace's latest runs, newest first; `--status <status>`, `--workflow <id>`, `--limit <n>`, `--dir <folder>`. A run whose model call waits for the answer to Studio's "Allow this address?" reads "! Needs you", "Waiting for your answer to "Allow this address?" in Studio, in the step <step>"; `halonic runs show` says who would send which key where. A finished run of a workflow with more than one ending names the one it reached first, such as "Ending: Finished without the reply · sent nothing" after a reject |
| `halonic runs show <run-id>` | shows what one run did; `--output` also shows what each step wrote, `--dir <folder>` picks the workspace. A run that waits for you shows the wait's title and, under it and before the "Answer with:" line, its body, such as, for the Support reply workflow, the reply it asks about and "Approving finishes the run. Nothing is sent." (`cli.commands.runs.show`). The title line is as the engine filled it in (`{{context.name}}` replaced), as the `runs` list does; a run logged before that falls back to the step's `description` as written in the workflow. A run with a connector that didn't start gets, after the step lines and a blank line, the same warning `halonic run` gives for it, such as "! handbook didn't start, so its tools are off in this run.", once for each connector (`cli.runs-show-connector-not-started`). A step with a failed call shows an indented "Didn't work." line under it, and a call refused because sending is off shows, after the steps and a blank line, one line: "! The call to send_mail (mail) wasn't made, because sending is turned off. Every `halonic plugin` command opens the plugin service with `openPluginService`
(`src/plugin-host.ts`): the profile's plugins folder and records, and the trust records plugins share
with workspaces, so they all read a plugin the same way. Nothing is created until a plugin is added.

A command that starts or moves on a run opens the workspace's engine with `openWorkspaceEngine`
(`src/workspace-engine.ts`): the stuck-step watch, and one signal that Ctrl C, SIGTERM, SIGHUP or a
step that keeps failing aborts. Once a command was stopped, closing the engine waits at most 15
seconds (`closeAfterStop` in `src/close-after-stop.ts`); a close that hangs is left behind, the
engine lock is released, and the process ends. It wraps the follow in `followUntilStopped` (`src/follow-run.ts`), which turns
Ctrl C into what stopping meant ("The run 01jd8q was cancelled after the step Classify it", or
"wasn't cancelled, only no longer followed, so it may go on" when the cancel failed) and
rethrows a stuck step's last error. `halonic run` and `halonic runs send` both use them, so there
is one engine opener.

While `halonic serve` holds the engine, `halonic run` doesn't open one: `startInServe`
(`src/commands/run/via-serve.ts`) asks `serve` over its console channel to start the run on its
engine, so the run shows in the phone's Inbox, and `run` prints the run's id. `serve` answers that
request in `src/commands/serve/serve-run-start.ts`, with the trust gate and executor of its own
start route. With `--event`, `--harness` or `--follow`, or no console to reach, `run` keeps the
lock's refusal (`cli.local-engine-lock`).

`halonic routines watch` passes `openWorkspaceEngine` an `onStuck`, so a stuck step is
reported and the watch goes on; without it, as for `run` and `runs send`, the step's last error
stops the command. A routine the watch starts whose saved changes aren't live yet gets the line
`routines list` gives it: "! Weekly report has changes that aren't live yet. It runs as last
committed until you commit them or make them live in Halonic Studio."
(`cli.commands.routines.watch-not-live`).

When `run`, `runs send`, `routines watch`, `routines list` or `serve` refuses a linked worktree, the
fix names the repository's own folder, and says that `test` and `validate` still work in the
worktree (`cli.repository-refused`).

## Environment

`HALONIC_HOME` picks the folder where Halonic keeps its data: trust records, runs, plugins and the
secrets you set with `halonic secret set`. Studio keeps its keys in the system keychain, so moving
the folder doesn't move them. Without `HALONIC_HOME`, Halonic uses `~/.local/share/halonic` on Linux (or
`$XDG_DATA_HOME/halonic`), `~/Library/Application Support/halonic` on macOS and
`%LOCALAPPDATA%\halonic` on Windows. The CLI and Studio share it, so set it in your shell's startup
file (such as `~/.zshrc`) and reopen Halonic after you change it. On Windows, set it as a user
environment variable instead. Use the full path of your home folder followed by
`\.halonic`: Windows doesn't turn `$HOME` into it there.

To move your data, for example when a run says the bridge's socket path is too long (Linux takes
at most 107 bytes, macOS 103), move the folder to a short path and point `HALONIC_HOME` at it.
On Linux with zsh, for example:

```sh
mv ~/.local/share/halonic ~/.halonic
echo 'export HALONIC_HOME="$HOME/.halonic"' >> ~/.zshrc
```

`HALONIC_HOME` must be a full path. Write `$HOME`, not `~`: inside quotes the shell doesn't turn `~`
into your home folder, and every command that uses Halonic's data folder then stops with
`HALONIC_HOME must be a full path, not "~/.halonic".`

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | it worked |
| 1 | the command ran and found errors, or failed |
| 2 | the command line was wrong (unknown command or option, missing argument) |
| 3 | the workspace isn't trusted on this machine, so nothing was started |
| 4 | not found: the thing asked for doesn't exist (`not_found`) |
| 5 | conflict: its state doesn't allow this now (`conflict`) |
| 6 | signed out: a sign-in is missing or has expired (`unauthenticated`) |
| 7 | not allowed: a rule says no (`denied`) |
| 8 | limit reached: a rate limit, quota or budget ran out (`limit_reached`) |
| 9 | unavailable: something Halonic needs is down; try again (`unavailable`) |

A command stopped by a closed terminal (SIGHUP), Ctrl C or SIGTERM ends with 129, 130 or 143.
1 is also a bug on our side (`internal`) and 2 a wrong value or file (`invalid_input`). The codes
never change meaning once released. `halonic --help` lists them too.

## Parity with the old CLI

`src/parity.test.ts` makes the 13 calls of the old CLI's `studio test` and `studio run` again with
`halonic test` and `halonic run`, each on a fresh copy of the parity base fixture, from the old fixed
clock, with IDs counted from 1 and the fixture trusted through the in-memory trust store. Each call

test. The compare, the rules and both lists live in `@halonicjs/testing-parity`; see its README

## Adding a command

1. Make a folder `src/commands/<name>/` with a `command.ts` that exports `<name>Command`
   (`run-tests` exports `runTestsCommand`), a `CliCommand`.
2. Put its requirements in `src/commands/<name>/requirements/` and its tests next to it.
3. Run `pnpm discover`. It writes the gitignored `src/generated/commands.ts`; turbo also runs it
   before every typecheck, test and build. The help is made from each command's `usage`, `summary`
   and `options`.
4. Add its name to `commandOrder` in `src/help.ts`, where `halonic --help` should list it; a
   test fails for a command that isn't there.

A command with subcommands, such as `runs show`, keeps them in its own folder and
lists them in its `subcommands` field, each a `CliCommand` named by its own word. The CLI hands
`halonic runs show <run-id>` to `show`, lists the subcommands in `halonic runs --help` and gives
the usage error for a word that isn't one of them, so the command never switches on its first
argument. A subcommand goes right after its command: for `halonic runs --limit 5 show <run-id>` the
CLI says `show` goes right after `runs`, before any options. A command that only hands off, such as `plugin`, leaves out `run`.

The help (`src/help.ts`) keeps every line within 80 columns, whatever the terminal's width: it
breaks a usage line between arguments, and a summary or option description between words, under
its own column. A word longer than the line stays whole (`cli.help`).

A command prints through the `CliIo` it is given, never `console`, and throws `UsageError` for a
wrong command line. It never prints an error itself: it throws a `KindedError` (with a `fix` when
there is a next step to suggest), and `printError` prints it and ends the command with the exit code
of its kind. An error without a kind is a bug: the CLI says so and exits with 1, without showing the
error's own text. Run it again with `--debug` (before or after the command) to see that text, its
causes and its stack, for a bug report.

A command that wants to tell an engineer something while it runs, such as a retry that may still
work out, passes the line to `context.debug`. It shows on stderr only with `--debug`, with loaded
secrets removed, and is never part of the result, so stdout and `--json` stay the same.

A command returns all its lines at the end. A line that is already final, such as a step's ✓ line
while a run goes on, it may also pass to `context.printAhead`: the CLI prints it at once (also
through a pipe and in CI, not with `--json`) and leaves it out at the end. The lines printed ahead
must be the first lines of the result, word for word; if they aren't, the CLI prints the whole
result, and the CLI's tests fail (`src/test/print-ahead-check.spec.ts` runs after every test).

A result may also carry `warnings`: `!` lines the CLI prints on stderr after the result, such as
`tools review`'s "2 tools from notes-mcp stay off: there's no terminal to ask you.". `--json` leaves
them out, since the document holds the result.
