# cli.commands.plugin.off-here

- Status: active
- Since: unreleased
- Source: HAL-15080, from check C540 #2 on HAL-15074; R13's words from microcopy 24.1 (HAL-751, approved on HAL-1949), as Studio's plugin page says them (`plugins.plugin-page-needs-yes`); the reason and fix in the CLI's own sandbox words (C566 #22, HAL-15361), with `doctor`'s docs line under them (C617-3, HAL-15716); the command holds no yes (`cli.no-unfenced-run-yes`); where the yes is given, and the warning before the question, from flow check C565 rows 2 and 5 (HAL-15351, HAL-15373); the question without "and turn it on", and the warning without a terminal, from flow check C626 #1 (HAL-15752); the same check and warning with a stale `--fingerprint`, from flow check C642 #4 (HAL-15865); the command offered as "To trust it anyway", not as the last step, from flow check C656 #3 (HAL-15947); the same with a stale `--fingerprint`, from Liam's review of #4971 (HAL-16016); `setup-needed`'s fix names `halonic sandbox setup` (C634 #4, HAL-15808)

Where a plugin's backend wouldn't run in the sandbox on this computer, as its start's gate decides from the platform and the sandbox check (`runnerFence`), the `halonic` command shall say a trusted plugin with a backend is off here, because it never runs plugin code without the sandbox. `halonic trust --plugin <id>` shall say "! *Name* is trusted, but off on this computer until you allow plugins and integrations to run without the sandbox." in place of "✓ *Name* is on now.", and "! *Name* is already trusted, but off on this computer until you allow plugins and integrations to run without the sandbox." in place of "is already on"; `halonic plugin add` shall say "! Added *Name* *version*. It's trusted, but off on this computer until you allow plugins and integrations to run without the sandbox." in place of "✓ Added *Name* *version*. It's on.". Each shall be followed by three indented lines: the reason and its fix in the words of `halonic doctor`'s Sandbox line, without "Then run halonic doctor again.", so no fix points to Studio's Settings; `halonic doctor`'s dimmed "More: *link* (*reason code*)" line, with the sandbox guide's section for the reason, since some fixes point to that page; then "Or allow this in the Halonic desktop app: Settings › Plugins › *Name* › Review. The halonic command runs plugin code only in the sandbox." Trust is still saved, and each still exits 0. When `halonic plugin add` or `halonic trust --plugin <id>` asks whether to trust such a plugin, the check's first line and the question shall be "Trust *Name*?", without "and turn it on", and it shall say before the question, after the check, "! Trusting *Name* won't turn it on: it stays off on this computer until you allow plugins and integrations to run without the sandbox." with the same three lines under it. With no terminal to ask, it shall say the same four lines after the check, before the line that says it is off because there's no terminal, and the command that trusts it shall follow "Read the list above. To trust it anyway, run:", since trusting it doesn't turn it on here. When `halonic trust --plugin <id>` refuses a `--fingerprint` that isn't the plugin's current one, the check it shows shall be the same, starting "Trust *Name*?", with the same three lines after it, before the line that says the fingerprint doesn't match. When `halonic plugin add` or `halonic trust --plugin <id>` refuses such a `--fingerprint` for such a plugin, the command that trusts it shall follow "Read the list above. To trust it anyway, run:" too. `halonic plugin list` shall show such a plugin that is on as "! off on this computer", with the same three lines under it. With `--json`, each shall give `offOnThisComputer`: the reason code, or for `plugin list` `null` when the plugin isn't off here, while `status` keeps its value. The sandbox shall be asked only when a plugin shown has a backend; in the sandbox, and for a plugin without a backend, the command shall say what it said before.

## Examples

- Given Weather, with a backend, added but off, on a computer where Halonic runs inside a container,
  when `halonic trust --plugin weather --yes --fingerprint <fingerprint>` is run,
  then Weather is trusted, it says "! Weather is trusted, but off on this computer until you allow plugins and integrations to run without the sandbox.", then "  Halonic is running inside a container, and the sandbox can't start there. Run Halonic on the computer itself, not in a container.", "  More: https://docs.halonic.dev/security/sandbox/#container (container)" and "  Or allow this in the Halonic desktop app: Settings › Plugins › Weather › Review. The halonic command runs plugin code only in the sandbox.", and exits 0.
- Given the same, trusted,
  when `halonic plugin list` is run,
  then Weather's line ends with "! off on this computer" and the same three lines follow it.
- Given Weather, trusted, on a computer where the sandbox's one-time setup isn't done,
  when `halonic plugin list` is run,
  then the line under it is "  The sandbox's one-time setup isn't done for this version of Halonic. Set it up with halonic sandbox setup. Windows asks for administrator rights once.", with no word of Settings, then "  More: https://docs.halonic.dev/security/sandbox/ (setup-needed)".
- Given Lister, with only a program, on the same computer,
  when it's added with `--yes --fingerprint <fingerprint>`,
  then it says "✓ Added Lister 1.0.0. It's on." and the sandbox isn't asked about plugin code.
- Given Weather, with a backend, inside a container,
  when `halonic plugin add` asks about it in a terminal,
  then the check starts with "Trust Weather?", and "! Trusting Weather won't turn it on: it stays off on this computer until you allow plugins and integrations to run without the sandbox." and the same three lines come right before the question "Trust Weather? [y/N]".
- Given the same, with no terminal,
  when `halonic plugin add` is run,
  then stderr has the check, then the same four lines, then "! Weather is added but off, because there's no terminal to ask you to trust it." and "  Read the list above. To trust it anyway, run: halonic trust --plugin weather --yes --fingerprint <fingerprint>", and it exits 3.
- Given Weather, with a backend, added but off inside a container, and a file of its copy changed since its fingerprint was shown,
  when `halonic trust --plugin weather --yes --fingerprint <that fingerprint>` is run,
  then stderr's check starts with "Trust Weather?", the same four lines come before "✕ That fingerprint doesn't match Weather as it is now.", the last line is "  Read the list above. To trust it anyway, run: halonic trust --plugin weather --yes --fingerprint <its fingerprint now>", and it exits 3.
