# workspace.local-only-sheet-hosts

- Status: active
- Since: unreleased
- Source: HAL-14300 (C42 of HAL-14271, HAL-5922, ADR `docs/adr/2026-11-08-local-first.md`); `run` reading the sheets of the version it starts is HAL-14860; counting a plugin's local tools is HAL-15094; a reason in every refusal of a plugin or integration connector is HAL-15396 (C570 #7); adding a plugin first, before turning off local-only, is HAL-15806 (C634 #2)

When `loadWorkspace` is given the hosts of the installed plugins and of the local integrations' sheets, and the workspace sets `privacy.localOnly: true`, the workspace package shall count a `plugin` or `integration` connector as local only when its own `local` key says `true` and its sheet is among those given and lists no host outside this computer and its network. A plugin's hosts are its backend's `hosts` and every local tool's `network` sites, so a plugin with only local tools is among those given too, and one that reaches nothing counts as local. A host is outside when it is a fixed host, whatever its name (the runner sends a name only to a public address), or a `{ fromSetting }` host of class `public`. Such a connector that isn't local gets an error that names its reason, so a local integration is never just said to be not local: when its sheet lists outside hosts, the plugin or the integration and every outside host, ending with `set privacy.localOnly: false in workspace.yaml to use it`, and never the `local: true` hint a program or an address gets; when its sheet isn't among those given, that the plugin isn't added here or can't be read, so nothing says which hosts it reaches, ending with `add the plugin first, then Halonic can tell whether it's local` and never the `privacy.localOnly: false` one, or that the integration's sheet can't be read, so nothing says which hosts it reaches, with the same ending as outside hosts; when its own `local` key says `false`, that it does, with the same ending; and when its sheet lists no outside host and its file has no `local` key, that the code reaches nothing outside this computer and its network but the connector doesn't say `local: true`, with the `local: true` hint and the `privacy.localOnly: false` one. `halonic validate`, `halonic run` before it starts anything, and the CLI's run connectors in a local-only run make the same decision with the same hosts, so a connector `validate` refuses is never started or called by a local-only run. `halonic run` shall read the local integrations' sheets from the files the run uses, the live version when the workspace has history, as its run connectors do, so a sheet saved but not made live changes neither decision.

## Examples

- Given `privacy.localOnly: true`, a connector with `local: true` to the plugin `acme-orders`, whose backend lists `api.acme.example`, when `halonic validate` runs, then it fails with `The plugin acme-orders reaches api.acme.example, so it isn't local: set privacy.localOnly: false in workspace.yaml to use it` at the connector's `local` key, and `halonic run` refuses the workspace before trust with `Acme has 1 problem in library/connectors/orders.connector.yaml. Nothing ran.`
- Given the same plugin listing only `orders.localhost`, when `halonic validate` runs, then it fails with `The plugin acme-orders reaches orders.localhost, …`: a fixed host never reaches this computer.
- Given the same plugin listing no hosts, when `halonic validate` runs, then it finds no problems.
- Given the same plugin listing no hosts, with a local tool whose `network` is `api.acme.example`, when `halonic validate` runs, then it fails with `The plugin acme-orders reaches api.acme.example, …`.
- Given a plugin `acme-files` with only a local tool and no `network`, and a `local: true` connector to it, when `halonic validate` runs, then it finds no problems.
- Given a local integration whose sheet lists a `public` host from its `server` setting, when it is loaded, then the error says `The integration in integrations/notes reaches the address in its server setting`.
- Given a plugin connector with `local: true` whose plugin isn't added, when it is loaded with the hosts, then it isn't local and the error is `The plugin acme-orders isn't added here or can't be read, so nothing says which hosts it reaches: add the plugin first, then Halonic can tell whether it's local`.
- Given a connector with no `local` key to the integration in `integrations/notes`, whose sheet lists only a `private` host, when it is loaded with the hosts, then the error is `The integration in integrations/notes reaches nothing outside this computer and its network, but connector "notes" doesn't say local: true: set local: true in its file, or set privacy.localOnly: false in workspace.yaml`.
- Given a local-only run whose hub has a `local: true` connector to a plugin that reaches `api.acme.example`, when the run's connectors start, then that connector isn't started and the run never calls it.
- Given a local-only workspace whose live version has a `local: true` connector to the integration in `integrations/station`, whose sheet lists `api.station.example`, and that sheet saved since with no hosts but not made live, when `halonic run` loads the workspace, then it has the error `The integration in integrations/station reaches api.station.example, …`; and with the two sheets the other way round, it has no such error.
