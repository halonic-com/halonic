# workspace.references

- Status: active
- Since: 0.1.0
- Source: HAL-1523 (HAL-186 implementation plan, step 1b; HAL-871); the provider of a hub's alias or of a `provider/model` setting, from Nina's C340 check (HAL-14301, code row C27, decided by the team on the task); a test of a failed workflow from the new-user flow check on HAL-12121 (HAL-12126); an alias of a failed provider from the first-run error check on HAL-14245 (HAL-14260); a name whose file failed, from the same check (HAL-14261)

When `loadWorkspace` has parsed a workspace's files, the workspace package shall report as an error every name a file gives that no parsed file of the right kind has where the name is looked up, with the file, the key path and line of the name, and the old loader's message, except the assistant model's, which names `assistant.model` and `models.yaml` (parity difference `assistant-model-alias-message`). The agents of a hub whose `hub.yaml` failed shall not be checked, as the old loader left that hub out. A file that is there where the name is looked up but failed its own checks still answers to its name (its own `id` when it has one and its text still reads, otherwise the one its file name gives), so that name shall not be reported as unknown, since that file's own errors are the cause: a workflow test's workflow (parity difference `test-of-failed-workflow-not-reported`), an alias's provider (parity difference `alias-of-failed-provider-not-reported`, HAL-14260), and an agent, workflow or library item named anywhere else (parity difference `failed-file-not-unknown`, HAL-14261). While `models.yaml` has failed, no model alias shall be reported as unknown, since any alias may be in it. The names are an agent's model aliases (its own and its methods'), skills, knowledge, collections, connectors and subagents; the providers and fallback aliases in `models.yaml`; the provider of each alias in a `hub.yaml` and of each `provider/model` setting (the workspace's and a hub's default model, the session AI, an agent and its methods), whose message ends with "Did you mean <provider>?" when one provider's id is near, or else says to add its file; the assistant model alias in `workspace.yaml` (`assistant.model`); and the workflow a workflow test targets.

An agent's skills, knowledge, collections and connectors are the hub's own or shared at the root; a hub that lists `uses` may use only the shared items it lists there. Model aliases are those of `models.yaml` and the hub's own. Subagents and a test's workflow are looked up in the same hub. A model given as `provider/model` is not an alias and isn't looked up among the aliases; its provider is looked up among the root's provider files.

## Examples

- Given each of the parity cases `agent/unknown-model`, `agent/unknown-method-model`, `agent/unknown-skill`, `agent/unknown-knowledge`, `agent/unknown-collection`, `agent/unknown-connector`, `agent/unknown-subagent`, `agent/own-subagent`, `hub/uses-leaves-out`, `models/unknown-provider`, `models/unknown-fallback` and `workflowTest/unknown-workflow`, when it is loaded, then it gives exactly the error the old loader recorded, at the key path and line its case file names.
- Given the parity case `workspace/unknown-model`, when it is loaded, then it gives the error `The assistant model (assistant.model) uses "turbo", which isn't an alias in models.yaml.` at the file, key path and line its case file names.
- Given the parity case `models/wrong-type`, whose `models.yaml` fails, when it is loaded, then only `models.yaml` has errors.
- Given each of the parity cases `hub/wrong-type`, `hub/missing-required`, `hub/unknown-key` and `hub/deep-nesting`, whose `hub.yaml` fails, when it is loaded, then no check reports an error for the hub's agents.
- Given each of the parity cases `workflow/missing-required` and `workflow/bad-indent`, whose workflow file fails, when it is loaded, then the workflow test next to it gets no "Test targets unknown workflow" error.
- Given each of the parity cases `provider/wrong-type`, `provider/missing-required`, `provider/unknown-key` and `provider/bad-format`, whose provider file `local-llm` fails, when it is loaded, then the alias `smart` on it gets no "uses unknown provider" error.
- Given `providers/mock.yaml` with `type: antropic` and an alias on `mock`, when it is loaded, then the only error is the provider file's `provider-type`; an alias on a provider no file names still gets `Alias "<alias>" uses unknown provider "<id>"`, as in the parity case `models/unknown-provider`.
- Given each of the parity cases `agent/unknown-key` and `agent/bad-enum`, whose agent file fails, when it is loaded, then only agent files have errors.
- Given a failed `writer.agent.yaml` with `id: author` and an agent with the subagents `author` and `writer`, when it is loaded, then only `writer` is an unknown agent.
- Given a hub without `uses` and an agent with a shared skill and one of the hub's own, when it is loaded, then there is no error.
- Given an agent at the root with the model `careful`, which only a hub defines, when it is loaded, then it uses an unknown model alias; an agent with `mock/echo` gets no error when `providers/mock.yaml` is there.
- Given `providers/mock.yaml`, a hub alias `careful` on the provider `mok` and an agent `writer` with the model `mok/echo`, when it is loaded, then the alias gets `Alias "careful" uses unknown provider "mok": Did you mean mock?` and the agent `Agent "writer" uses model "mok/echo", whose provider "mok" the workspace doesn't have: Did you mean mock/echo?`.
- Given a hub agent with a subagent that exists only at the root, when it is loaded, then it delegates to an unknown agent.
