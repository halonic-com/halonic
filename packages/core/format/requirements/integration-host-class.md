# format.integration-host-class

- Status: active
- Since: unreleased
- Source: HAL-3385; the design on HAL-1873, section 5 (Julian's option A on HAL-1939), approved by the board on HAL-1949; Tailscale's `100.64/10` counted as private on HAL-14783 (Liam); a host name in a `private` setting on HAL-15005 (Liam)

The format shall require a permission sheet's `{ fromSetting }` host in `hosts` to declare its class, `loopback`, `private` or `public`, so the trust check can say where it may go before the setting is filled in; a secret shall name such a host by its setting alone; and `integrationPolicy` shall refuse, as `setting-outside-class`, a setting whose URL's host is outside that class: `loopback` takes only `localhost`, `127.0.0.0/8` and `[::1]`; `private` a private IP address (`10/8`, `172.16/12`, `192.168/16`, the shared range `100.64/10` that Tailscale's addresses sit in, `fc00::/7`), apart from Tailscale's own service address `100.100.100.100` and the metadata address `100.100.100.200`, or a host name other than `localhost` and `*.localhost` over `https`; `public` only a host name other than `localhost` and `*.localhost`, over `https`. An address in no class, such as link-local `169.254.0.0/16`, `[::]` or `100.100.100.100`, is refused by every class. On some ISPs `100.64/10` is the carrier's own network rather than the user's, so a `private` setting there reaches the carrier's devices; the setting is still the user's own, and the trust check shows it. The class check reads only the URL's text, so it can't prove where a name in a `private` setting points: `integrationPolicy` lists such a name in the policy's `privateNames`, and the integration's transport shall look the name up on every request and connect only to the private addresses of the answer, or refuse the integration (`private-name-unchecked`) when it can't.

## Examples

- Given `hosts: [{ fromSetting: url }]` without a class, or with `class: anywhere`, when it is parsed, then it fails at `hosts[0]`.
- Given a secret whose host is `{ fromSetting: url, class: public }`, when it is parsed, then it fails with `unrecognized_keys`: the class sits in `hosts`.
- Given `class: loopback` and `url` set to `http://localhost:8080`, `http://127.0.0.2` or `https://[::1]:8443`, when the policy is resolved, then it passes; with `http://192.168.1.5` or `https://mcp.example.com`, it fails with `setting-outside-class`.
- Given `class: private` and `url` set to `http://192.168.1.5:8123`, `https://[fd12::1]`, `https://100.116.12.34`, `https://nas.example.com` or `https://box.tail1234.ts.net:8443`, when the policy is resolved, then it passes; with `http://localhost:8123`, `https://localhost`, `https://app.localhost`, `https://[fe80::1]`, `https://100.100.100.100`, `https://100.100.100.200` or `https://100.128.0.1`, it fails with `setting-outside-class`.
- Given `class: private` and `url` set to `http://nas.example.com`, when the policy is resolved, then it fails with `plain-http-not-local`, as for `class: public`.
- Given `class: private` and `url` set to `https://box.tail1234.ts.net`, when the policy is resolved, then its `privateNames` are `box.tail1234.ts.net`; with `https://192.168.1.5` or a `public` setting, there are none.
- Given that integration opened through the CLI's transport, when the name resolves to `93.184.215.14`, to `100.100.100.100`, or only to addresses outside every private range, then the request is refused before any connection; when it resolves to `93.184.215.14`, `100.116.12.34` and `10.0.0.5`, then the connection is handed only `100.116.12.34` and `10.0.0.5`; on a transport without `withPrivateNames`, the integration is refused with `private-name-unchecked` and no runner starts.
- Given `class: public` and `url` set to `https://mcp.example.com`, when the policy is resolved, then it passes; with `https://localhost`, `https://app.localhost`, `https://10.0.0.7`, `https://8.8.8.8` or `https://[::]`, it fails with `setting-outside-class`, and with `http://mcp.example.com` with `plain-http-not-local`.
- Given `https://169.254.169.254`, `https://[::]` or `https://100.100.100.100`, when the policy is resolved under each class, then every class fails with `setting-outside-class`.
- Given a refused setting, when its problem is read, then the message names what the class allows and the host it got.
