# format.workspace-snapshot

- Status: active
- Since: unreleased
- Source: HAL-17948, HAL-18049, HAL-18141, HAL-17980 (plan HAL-17450 rev 5, "How the plugin reads the workspace" and "Safety")

The format shall define the workspace snapshot as plain, engine-neutral data: `format` (1), `workspace` with its `name` (1 to 80 characters, no hidden marks) and `commit` (a full lowercase SHA-1 or SHA-256 id), and `tools`, at most 200 tool files in the `format.tool-file` shape with every default filled in, optionally `templates`, at most 100 templates in the `format.template-file` shape, optionally `signals`, at most 50 signal files in the `format.signal-file` shape with every default filled in, and no other key at any depth. When `makeSnapshot` is given templates or signals, it shall sort each by id, and it shall leave `templates` or `signals` out when there are none, so a workspace without them gets the same snapshot text as before. When `makeSnapshot` is given a workspace's name, commit and parsed tools, it shall sort the tools by name and check the result as `readSnapshot` does. When `readSnapshot` reads a snapshot, it shall return it whole or refuse it whole, with every problem: the schema's, `value-looks-like-key` at `workspace.name` when the name holds a key by the rules of `format.keys-in-values`, each tool's `format.tool-refusals` at `tools[i]`, `tool-name-twice` or `tool-id-twice` where a name or id is used again, `tools-not-sorted` at the first tool out of name order, `value-looks-like-key` at `templates[i]` for a key in a template's title or body, `template-id-twice` where a template id is used again, `templates-not-sorted` at the first template out of id order, each signal's `format.signal-refusals` at `signals[i]`, `signal-id-twice` or `signal-rule-twice` where a signal's id or rule is used again (two signals for one rule would leave it unclear which settings count), and `signals-not-sorted` at the first signal out of id order. When `readSignal` reads one entry of a snapshot's `signals` list, it shall check it with the signal file's schema and `format.signal-refusals` and return it with its defaults filled in, or every problem, so a reader can turn off that one signal. When `readSnapshotText` reads a snapshot's text, it shall refuse text over 4 MiB with `snapshot-too-large` and text that isn't JSON with `snapshot-not-json`, both before parsing it further, and otherwise read it as `readSnapshot` does. `snapshotText` shall write a snapshot as canonical JSON, so the same tools in any order give the same text. The snapshot's JSON Schema shall equal the committed `spec/workspace-snapshot.schema.json`.

## Examples

- Given the tools `task_get` and `my_prs`, when the snapshot is made, then they are listed `my_prs` first, and reading its text back gives the same snapshot.
- Given the templates `pr-body` and `card` and no templates, when the snapshots are made, then the first lists `card` first and the second has no `templates` key.
- Given two templates with the id `card`, `pr-body` before `card`, or a key in a template's body, when it is read, then it is refused with `template-id-twice`, `templates-not-sorted` or `value-looks-like-key` there.
- Given the same tools in two orders, when both snapshots are written, then the texts are equal.
- Given `format: 2`, a `secrets` key, a seven-digit commit or a tool whose action is `shell.run`, when it is read, then it is refused there.
- Given a tool with a `token` parameter and another with a key in its description, when the snapshot is read, then it is refused with `parameter-asks-for-key` at `tools[0].parameters.token` and `value-looks-like-key` at `tools[1].description`.
- Given a workspace name holding an Anthropic key, when the snapshot is read, then it is refused with `value-looks-like-key` at `workspace.name`.
- Given two tools named `my_prs`, two with the same id or `b_two` before `a_one`, when it is read, then it is refused with `tool-name-twice`, `tool-id-twice` or `tools-not-sorted` at the second tool.
- Given a snapshot text of 4 MiB and one byte, when it is read, then it is refused with `snapshot-too-large` only; given `{`, it is refused with `snapshot-not-json`.
- Given 201 tools, when it is read, then it is refused at `tools`.
- Given one `pr-watcher` signal, when the snapshot is made and its text read back, then the signal is kept; given none, the snapshot has no `signals` key.
- Given two signals with the id `a`, or `b` before `a`, both on `pr-watcher`, when it is read, then it is refused with `signal-rule-twice` at the second signal's `rule.run`, and with `signal-id-twice` or `signals-not-sorted` there.
- Given a signal whose id is a key, whose rule is `shell.run` or that has an `action`, when it is read, then it is refused at that signal.
- Given one `signals` entry with only an id and `rule: { run: pr-watcher }`, when `readSignal` reads it, then `done` is `true` and `dryRun` is `false`; given one whose id is a key, it is refused with `value-looks-like-key` at `id` and the problem doesn't hold the key; given `rule: { run: deploy }`, it is refused at `rule.run`.
