# Where the old code gives no line, or a wrong one

Recorded from the old repo at `784f78d` on the fixtures in this folder. Each
case's `case.json` says on which line its fault really is (`expect.line`); the
recorder compares that with the first error or warning the old loader gives
for the file. `old-line-notes.json` lists every case where they differ. It is
generated by the recorder; this page sums it up.

These are **candidates** for the allowed-differences file of the compare task.
Nothing here is decided yet: each one gets a requirement ID and Liam's sign-off
there, or the new code copies the old behaviour.

Of 144 cases with an expected line: 68 match, 22 give a different line, 53 give no
line, and 1 reports the error on another file.

## The `validate` command never prints a line

The old `studio validate` prints `error <path>: <message>` and drops the line
and column the loader worked out. Every line in the recordings comes from the
loader itself (`loadWorkspace`), not from the command's output.

## No line at all (53 cases)

Only schema and YAML errors get a line. Everything checked after the files are
parsed has none:

- **References between files**: unknown model alias, provider, fallback,
  skill, knowledge source, collection, connector, subagent, workflow, hub,
  method; a hub's `uses` that leaves out what an agent needs; a test for an
  unknown workflow; the default deployment that isn't listed.
- **Workflow rules** (`validateWorkflow`): each of its 18 checks names the
  state but gives no line, for example a dead end, an unreachable state or a
  timer outside a wait state. Method calls (missing or extra arguments) too.
- **Loops**: agents that delegate to each other, workflows that run each other.
- **Routine triggers**: a bad cron field or an unknown time zone.
- **Connector rule**: a tool that needs approval but isn't allowed (a warning).
- **Skills**: any fault in a `SKILL.md` (no front matter, missing description,
  wrong type, bad YAML) gives the same message, "SKILL.md needs front matter
  with name and description", without a line.

## A different line (22 cases)

- **Unknown keys** (12 cases): the line of the map that holds the key, not of
  the key. At the top of a file that is line 1 (or the first key after a
  comment), however far down the unknown key is.
- **Missing keys** inside a map (3 cases): the first line of the map's
  contents, not the line of the key that owns the map. (At the top of a file
  both are the same line, so those cases match.)
- **Bad record keys** (2 cases), such as a method or deployment name with
  capitals: the line of the value, one below the key.
- **Unions** (3 cases): a fault inside `transport` or a routine `trigger` points
  at `transport:` or `trigger:`, because the schema can't tell which variant was
  meant.
- **YAML errors** (2 cases): an unclosed quote is reported at the end of the
  file (line 23 for a fault on line 4); a wrongly indented key one line early.

## The error lands on another file (1 case)

`provider/duplicate-id`: a new file `providers/mock-copy.yaml` repeats the id of
`providers/mock.yaml`. Files load in sorted order, so the new file wins and the
error is reported on the old, correct file.

## Other old behaviour worth knowing for the compare task

- **The `15m` bug** (`routine/mail-every-15m`): the mail trigger's `every`
  pattern is `^[1-9]d*(m|h|d)$` (a missing backslash), so any interval with
  two or more digits, such as `15m`, is rejected. One-digit intervals pass
  (`routine/mail-every-1d`). The fixture marks `15m` as valid; the recording
  shows the old error on line 7.
- **Paths in messages are not the paths on disk.** The loader reads through a
  layout mapping, so a file at `library/connectors/files.connector.yaml` is
  reported as `connectors/files.connector.yaml`, and
  `hubs/billing/workflows/routines/…` as `hubs/billing/routines/…`. Each
  recording keeps both: `file` (on disk) and `flatPath` (as the loader names it).
- **One bad file causes errors in others.** A workflow that fails its schema is
  left out, so its test file and the routines that run it report "unknown
  workflow" as well (`workflow/unknown-key` gives 4 errors for one fault).
- **Warnings don't fail `validate`**: exit code 0 with warnings only.
- **Files the loader skips** are recorded as `not-read`: an agent file in a
  sub-folder of `agents/`, a `SKILL.md` one folder too deep.
- **The file name gives the id** when a file has none (`provider/id-from-file-name`).
- **Old names still load** with an info message: `org.yaml`, `projects/`,
  `flows/`, `flow:` in tests, `run.flow` and `run.project` in routines.
